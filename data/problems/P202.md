# P202 주문번호로 주문 찾기

> 2장 · 2.2.7 자동 형변환

주문번호가 `0000123456`인 주문의 주문 ID(`order_id`), 고객 번호(`cust_id`), 금액(`amount`)을 조회하세요.

비효율 쿼리는 주문번호 인덱스가 있는데도 20만 건을 다 읽어요. **`order_no`의 데이터 타입**을 확인해 보세요.

- 사용 테이블 (데이터셋 `shop`)
  - `study.customers` 고객 1만 명 — `customers_pk`(cust_id), `cust_grade_ix`(grade). grade: VIP 1%·GOLD 9%·NORMAL 90%
  - `study.orders` 주문 20만 건, 고객당 20건, 2025-01-01~2026-12-31 (하루 약 274건)
    - `orders_pk`(order_id), `ord_cust_date_ix`(cust_id, order_date), `ord_cust_amt_ix`(cust_id, amount),
      `ord_date_ix`(order_date), `ord_no_ix`(order_no), `ord_status_date_ix`(status, order_date)
    - 주문일 순서로 적재되어 **주문일 인덱스는 클러스터링이 좋고**, 고객 번호는 흩어져 있어 **고객 인덱스는 나쁘다**
    - `order_no`는 숫자로 된 **문자열**(예: `'0000012345'`), `status`는 A~E 각 20%

## 스키마

```sql
-- 2~5장 데이터셋: 고객 1만 명, 주문 20만 건 (주문당 메모 150바이트 → 테이블이 인덱스보다 훨씬 크다).
-- 주문은 order_id 순서 = 주문일 순서로 적재 → 주문일 인덱스는 클러스터링이 좋고,
-- 고객 번호는 주문마다 흩어져 있어 고객 인덱스는 클러스터링이 나쁘다.
CREATE TABLE customers (
  cust_id    NUMBER        NOT NULL,
  cust_name  VARCHAR2(30)  NOT NULL,
  grade      VARCHAR2(10)  NOT NULL,   -- VIP 1%, GOLD 9%, NORMAL 90%
  region     VARCHAR2(10)  NOT NULL,   -- 서울·부산·대구·광주·대전 (5개)
  memo       VARCHAR2(150),
  CONSTRAINT customers_pk PRIMARY KEY (cust_id)
)
/
CREATE INDEX cust_grade_ix ON customers (grade)
/
CREATE TABLE orders (
  order_id    NUMBER        NOT NULL,
  cust_id     NUMBER        NOT NULL,
  order_date  DATE          NOT NULL,   -- 2025-01-01 ~ 2026-12-31, 하루 약 274건
  order_no    VARCHAR2(10)  NOT NULL,   -- 숫자로 된 문자열 주문번호 (예: '0000012345')
  status      VARCHAR2(1)   NOT NULL,   -- A·B·C·D·E 각 20%
  amount      NUMBER(10)    NOT NULL,
  memo        VARCHAR2(150),
  CONSTRAINT orders_pk PRIMARY KEY (order_id)
)
/
CREATE INDEX ord_cust_date_ix ON orders (cust_id, order_date)
/
CREATE INDEX ord_cust_amt_ix ON orders (cust_id, amount)
/
CREATE INDEX ord_date_ix ON orders (order_date)
/
CREATE INDEX ord_no_ix ON orders (order_no)
/
CREATE INDEX ord_status_date_ix ON orders (status, order_date)
/
```

목표: Buffers ≤ 18
