## 3.3 인덱스 스캔 효율화
인덱스 스캔 효율화란 동일한 결과 건수를 반환하더라도, 인덱스의 시작점과 종료점을 최적화하여 불필요한 Leaf 블록 및 인덱스 엔트리 탐색을 최소화 하는 것이다.
인덱스 스캔 효율이 좋은지 나쁜지 확인하는 방법은 SQL trace에서 확인할 수 있다. 
인덱스를 스캔하고 얻은 레코드가 10건인데, 그 과정에서 SQL trace에서 표시되는 것 중 하나인 cr(Consistent Read, 읽기 일관성을 유지하면서 블록을 읽는 논리적 I/O)을 
7000개 블록을 읽었다면, 많은 데이터를 읽고 열 개를 얻은 것이다.

### 인덱스 조건과 필터 조건

+ **Index Access**: 인덱스 스캔 범위를 결정하는 조건절
+ **Index Filter**: 이미 읽은 인덱스 엔트리에서 조건을 추가 검사 하는 필터 -> Index Access에서 읽은 ROWIDF를 테이블에 전달할지 추가로 판단하는 선택적인 과정
+ **Table Random Access**: Index Access에서 인덱스 범위 스캔 시 얻은 ROWID로 테이블 블록을 읽음
+ **Table Filter**: 테이블 액세스 단계에서 조건절을 검사해 행을 걸러내는 작업

인덱스를 이용한 테이블 액세스 비용 = 인덱스 수직적 및 수평적 탐색 비용 + 테이블 랜덤 액세스 비용
                          = 인덱스 루트와 브랜치에 레벨에서 읽는 블록 수 + 인덱스 리프 블록을 스캔하는 과정에 읽는 블록 수 + 테이블 액세스 과정에 읽는 블록 수


### 비교 연산자, 컬럼 순서에 따른 군집성
선행 컬럼이 모두 '=' 조건인 상태에서 첫 번째 나타나는 범위검색 조건까지만 만족하는 인덱스 레코드는 모두 연속해서 모여있지만,
그 이하 조건까지 만족하는 레코드는 비교 연산자 종류에 상관없이 흩어진다.

앞서 말한 군집성과 이어서 인덱스 선두 또는 선행 컬럼이 등치(=) 조건이 아닐 때
나머지 조건들은 흩어져 있기 때문에 조건을 만족하지 않는 레코드까지 스캔하고 버리는 비효율이 생긴다.

범위검색 조건(BETWEEN, LIKE)이 어쩔 수 없이 인덱스 선두 컬럼에 있다면 IN절을 사용해 
위와 같은 상황에서 비교적 효율적으로 사용할 수 있다. 그 이유는 각 IN절에 있는 조건으로 수직적 탐색이 n번 일어나고,
인덱스 스캔범위를 줄일 수 있기 때문이다. 다만, IN-List 개수가 많으면 그만큼 수직적 탐색 비용이 많이 발생하므로 유의해야한다.

**IN 조건은 등치조건(=)과 같은 걸까?**
IN 절은 사실 OR절과 같은 의미이다. 인덱스 액세스 조건으로 되면 IN-List Iterator 방식으로 적용될 수 있고,
이때는 등치조건과 같은 의미가 된다. 무조건, IN-List Iterator 방식으로 푸는 것이 항상 효과적인가?

``` sql
-- 상품_pk : 상품id
-- 상품_x01 : 상품id + 상품구분코드

select * from 상품
where 상품id = :prod_id
      and 상품구분코드 in('GX', 'KR')
```

위와 같은 SQL에서 실행 계획 및 Predicate Information을 확인해보니 상품 id는 인덱스 액세스를 하고,
상품구분코드는 인덱스 필터가 선택되었다. 인덱스 구성을 '상품구분코드 + 상품id' 로 변경해서 IN-List Iterator 방식으로 푸는게
더 효과적일까? 그렇지 않다 그 이유는 상품_x01 인덱스를 사용하면 상품 id는 pk이기 때문에 바로 찾아갈 수 있어 인덱스 탐색 범위가 작다.
만약 인덱스를 변경한다면 수직적 탐색도 2번(GX + 상품id, KR + 상품id) 타게 되므로 상품_x01 인덱스보다 비효율적인 탐색이 존재한다.

**따라서 상품ID가 PK인 상황에서는 IN-LIST ITERATOR를 유도하기 위해 인덱스 순서를 변경할 실익이 작으며, 반복 탐색으로 인해 오히려 비효율적일 수 있다.**

힌트를 사용해서 IN-List를 액세스 조건 또는 필터 조건으로 유도하는 방법이 있다.

``` sql
select /*+ num_index_keys(idx_x01 1)*/ -- 인덱스이름, 적용할 인덱스 컬럼 범위(1은 인덱스 첫 번째 컬럼까지만 액세스 조건으로 사용하라는 의미)
  from orders
  where custNo = :cust_no
       and orderID IN(......)
```

### BETWEEN과 LIKE
결론부터 말하자면 범위검색 조건을 사용할 때 BETWEEN을 사용하는 것이 손해는 안본다.
그 이유는 스캔 범위에서부터 있다.
``` sql
-- #1
  where 구분 = 'B'
       and BETWEEN '202601' AND '202612'

-- #2
  where 구분 = 'B'
       LIKE '2019%'
```

위 쿼리에서 인덱스가 '판매월+판매구분'으로 구성되어있고 구분 값이 A가 90프로, B가 10프로라고 해보자. 
1번째는 년월이 각 시작점 명확한 반면 2번째는 상대적으로 명확하지 않다 따라서, 2번째는 202600도 저장되어 있다면
그 값도 읽어야 하므로 구분 'B'인 지점으로 바로 내려갈 수 없고 202601 첫 번째 레코드에서 스캔을 시작한다.

### 범위 검색 조건을 옵션 조건에 남용하면 생기는 비효율
인덱스 컬럼이 선택적 검색 조건으로 사용되는 상황에서, 옵션 조건을 처리하기 위해 범위 검색 조건을 남용하면 인덱스 스캔 효율이 저하될 수 있다.
LIKE/BETWEEN 조건을 활용하고 싶으면 아래 네 가지 경우를 점검해야 한다.
1. 인덱스 선두 컬럼
2. NULL 허용 컬럼
3. 숫자형 컬럼
4. 가변길이 컬럼

비효율을 줄이기 위해 UNION ALL, NVL/DECODE를 활용할 수 있다.
NVL/DECODE는 OR Expansion 쿼리 변환이 이뤄져 인덱스 액세스 조건으로 사용할 수 있는 장점이 있다.
단, NULL 허용 컬럼에는 사용할 수 없다.
``` sql
  where 고객ID = NVL(:cust_id, 고객ID)
  ..
  where where 고객ID = decode(:cust_id, null, 고객ID, cust_id)
```
해당 구문을 COALESCE나 CASE문으로 교체해도 될거 같지만 OR Expansion 쿼리 변환이 이뤄지기 작동하기 위해서는
NVL/DECODE를 사용해야한다. 해당 함수에 대해 쿼리 변환이 이뤄지도록 하는 히든 파라미터는 '_or_expand_nvl_predicate' 이다.

위와 같은 비효율을 없애기 위해 Dynamic SQL를 이용해 조건절을 동적으로 구성할 수 있다.
예를들어, iBatis 같은 SQL 매핑 프레임워크에서는 옵션 조건을 사용할 수 있다.
