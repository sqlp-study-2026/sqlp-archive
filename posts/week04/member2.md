## 3.3 인덱스 스캔 효율화
인덱스 스캔 효율화란 동일한 결과 건수를 반환하더라도, 인덱스의 시작점과 종료점을 최적화하여 불필요한 Leaf 블록 및 인덱스 엔트리 탐색을 최소화 하는 것이다.
인덱스 스캔 효율이 좋은지 나쁜지 확인하는 방법은 SQL trace에서 확인할 수 있다. 
인덱스를 스캔하고 얻은 레코드가 10건인데, 그 과정에서 SQL trace에서 표시되는 것 중 하나인 cr(Consistent Read, 읽기 일관성을 유지하면서 블록을 읽는 논리적 I/O)을 
7000개 블록을 읽었다면, 많은 데이터를 읽고 열 개를 얻은 것이다.

### 인덱스 조건과 필터 조건

+ **Index Access**: 인덱스 스캔 범위를 결정하는 조건절
+ **Index Filter**: 이미 읽은 인덱스 엔트리에서 조건을 추가 검사 하는 필터 -> Index Access에서 읽은 ROWIDF를 테이블에 전달할지 추가로 판단하는 선택적인 과정
+ **Table Random Access**: Index Access에서 인덱스 범위 스캔 시 얻은 ROWID로 테이블 블록을 읽음
+ **Table Filter**: 테이블 액세스 단계에서 조건절을 검사해 행을 걸러내는 작업

인덱스를 이용한 테이블 액세스 비용 = 인덱스 수직적 및 수평적 탐색 비용 + 테이블 랜덤 액세스 비용
                          = 인덱스 루트와 브랜치에 레벨에서 읽는 블록 수 + 인덱스 리프 블록을 스캔하는 과정에 읽는 블록 수 + 테이블 액세스 과정에 읽는 블록 수


### 비교 연산자, 컬럼 순서에 따른 군집성
선행 컬럼이 모두 '=' 조건인 상태에서 첫 번째 나타나는 범위검색 조건까지만 만족하는 인덱스 레코드는 모두 연속해서 모여있지만,
그 이하 조건까지 만족하는 레코드는 비교 연산자 종류에 상관없이 흩어진다.

앞서 말한 군집성과 이어서 인덱스 선두 또는 선행 컬럼이 등치(=) 조건이 아닐 때
나머지 조건들은 흩어져 있기 때문에 조건을 만족하지 않는 레코드까지 스캔하고 버리는 비효율이 생긴다.

범위검색 조건(BETWEEN, LIKE)이 어쩔 수 없이 인덱스 선두 컬럼에 있다면 IN절을 사용해 
위와 같은 상황에서 비교적 효율적으로 사용할 수 있다. 그 이유는 각 IN절에 있는 조건으로 수직적 탐색이 n번 일어나고,
인덱스 스캔범위를 줄일 수 있기 때문이다. 다만, IN-List 개수가 많으면 그만큼 수직적 탐색 비용이 많이 발생하므로 유의해야한다.

## 3.3.12 함수호출 부하 해소
PL/SQL 사용자 정의 함수는 인터프리터 언어, 호출 시마다 컨텍스트 스위칭 발생, 내장 SQL에 대한 Recursive Call 발생으로 느리다.
따라서, 함수 호출 횟수를 줄이는 방법 중 하나로 액새스 조건을 고려한 인덱스 구성이다. 해당 함수를 조건절에 사용한다면 단독으로 사용하는 것이 아닌
행수를 줄여줄만한 조건을 선두에 넣든, 인덱스를 지정해서 선두 컬럼을 넣든 호출 횟수를 줄여줘야 한다.

또한, 해당 함수가 select 절에 사용될 수 있다. 이때는 스칼라 서브쿼리를 사용하여 캐싱을 시켜주는 기법으로 사용하면 된다.
