## 3.1 테이블 액세스 최소화

### 테이블 랜덤 액세스

인덱스를 사용하더라도 대량의 데이터를 조회하면 테이블 풀 스캔보다 오히려 느려질 수 있다.

- SQL에서 참조하는 컬럼을 인덱스가 모두 포함하지 않는다면, 인덱스 스캔 후 테이블을 추가로 액세스해야 한다.
- 실행 계획에는 `TABLE ACCESS BY INDEX ROWID`로 표시.

#### ROWID와 테이블 액세스

ROWID는 테이블 레코드의 물리적 위치를 식별하기 위한 논리적 주소 정보다.

- 예시 : ROWID는 우편번호 / 포인터는 전화번호 같은 것.
- 인덱스 리프 블록에서 ROWID를 확인 -> DBA 정보를 얻음 -> 버퍼 캐시 있없 찾기 -> DBA 이용해서 해시함수 해시체인 찾음 -> 버퍼 헤더 찾음 -> 헤더가 가리키는 버퍼 블록..
- 디스크 I/O 필요하면 디스크 갔다가 버퍼 캐시에 넣고 위의 과정.. 

#### 인덱스 스캔과 풀 스캔의 블록 탐색 차이

- 인덱스 스캔: 리프 블록에서 ROWID를 얻고, ROWID를 통해 테이블 블록의 DBA를 확인한다.
- 테이블 풀 스캔: 세그먼트의 익스텐트 정보를 이용해 읽을 데이터 블록의 위치를 파악한다.

이러한 탐색 과정에서 동시 액세스가 많아지면 캐시 버퍼 체인 래치(Latch), 버퍼 락(Buffer Lock) 등의 경합이 발생할 수 있다.


### 인덱스 클러스터링 팩터(Clustering Factor)

클러스터링 팩터는 **인덱스의 정렬 순서와 테이블 데이터의 물리적 저장 순서가 얼마나 유사한지**를 나타내는 지표다.

- 같은 인덱스 키 순서로 데이터를 조회했을 때 테이블 블록이 물리적으로 모여 있으면 클러스터링 팩터가 좋다. -> 찾는 속도가 빠름

**클러스터링 팩터의 효과**

- 클러스터링 팩터가 좋으면 테이블 액세스 횟수에 비해 실제 블록 I/O가 적게 발생할 수 있다.
- 인덱스 스캔 중 직전에 읽은 테이블 블록과 다음에 읽을 테이블 블록이 같다면, 포인터를 해지하지 않고 유지하는데 이 관련 기법 버퍼 피닝
- 그걸 이용해서 해당 블록을 다시 찾는 일부 논리적 탐색 과정을 생략할 수 있음.
- 다음 인덱스 레코드가 직전에 읽은 것과 동일한 테이블 블록을 가리키면 버퍼 탐색 과정을 줄일 수 있다.
- 클러스터링 팩터가 나쁘면 인덱스 레코드마다 서로 다른 테이블 블록을 찾아가는 경우가 많아진다.

### 인덱스 손익분기점

인덱스 손익분기점은 인덱스 레인지 스캔이 테이블 풀 스캔보다 느려지는 지점.

| 구분 | 테이블 풀 스캔 | 인덱스 레인지 스캔 |
|---|---|---|
| 접근 방식 | 시퀀셜 액세스 | 인덱스 범위 탐색 및 테이블 랜덤 액세스 |
| I/O 특성 | 멀티블록 I/O 활용 | 싱글블록 I/O가 자주 발생 |

### 온라인 프로그램 튜닝 VS 배치 프로그램 튜닝

| 구분 | 온라인 프로그램 | 배치 프로그램 |
|---|---|---|
| 데이터 처리 | 소량의 데이터 | 대량의 데이터 |
| 주요 튜닝 방향 | 응답 시간 최소화 | 전체 처리 시간 최소화 |
| 대표적인 방식 | NL 조인, 인덱스 활용 | 해시 조인, 풀 스캔 |
| 데이터 액세스 | 필요한 데이터만 빠르게 조회 | 전체 범위 처리 고려 |

**배치 프로그램에서는 파티션 활용 전략도 중요하다.**

테이블 파티셔닝은 FULL SCAN을 빠르게 처리하기 위함. 
그래서 파티셔닝 된 테이블에 인덱스를 쓰더라도.. 쿼리 성능이 그닥.. 

### Covered 쿼리와 INCLUDE 인덱스

#### Covered 쿼리 / Covered Index

- Covered 쿼리: SQL에서 필요한 컬럼을 인덱스만으로 모두 처리할 수 있는 쿼리
- Covered Index: 해당 쿼리에 필요한 컬럼을 모두 포함하고 있는 인덱스

인덱스만으로 필요한 데이터를 처리할 수 있으므로 테이블 랜덤 액세스를 줄일 수 있다.

#### INCLUDE 인덱스

인덱스 키 컬럼 외에 추가 컬럼을 리프 블록에 저장하는 방식이다.

- 인덱스 키 컬럼: 루트·브랜치·리프 블록에 저장되며 인덱스 탐색에 사용된다.
- INCLUDE 컬럼: 리프 블록에만 저장되며 인덱스 탐색 조건(수직적탐색)에는 사용되지 않는다.
- INCLUDE 컬럼은 테이블 랜덤 액세스를 줄이는 용도로 활용한다.
- INCLUDE 컬럼은 인덱스 키가 아니므로 해당 컬럼을 이용해 소트 연산을 생략할 수는 없다.

### 인덱스 구조 테이블(IOT: Index-Organized Table)

테이블 자체를 인덱스 구조로 저장하는 방식.

- 일반 테이블은 데이터가 힙(Heap) 구조로 저장되고, 인덱스는 별도로 존재한다.
- IOT는 테이블 데이터를 인덱스 구조의 리프 블록에 저장한다.
- 따라서 일반 테이블처럼 ROWID를 이용해 별도의 테이블 블록을 찾아갈 필요가 없다.
- 시퀀셜 방식으로 데이터를 액세스 하기 때문에 범위 탐색할 때 유리 

**일반 테이블과 IOT 비교**

| 구분 | 일반 테이블 | IOT |
|---|---|---|
| 데이터 저장 | 힙 구조 | 인덱스 구조 |
| 인덱스 리프 | ROWID 저장 | 실제 테이블 데이터 저장 |
| 데이터 조회 | 인덱스 → ROWID → 테이블 | 인덱스에서 데이터 직접 조회 |

생성 시 다음과 같이 지정한다.

```sql
CREATE TABLE EMP (
    EMP_NO NUMBER PRIMARY KEY,
    EMP_NM VARCHAR2(100)
)
ORGANIZATION INDEX;
```

IOT는 데이터를 인덱스 구조에 저장함으로써 인덱스 키 기준의 클러스터링 효과를 얻는 방법 중 하나다.

### 클러스터 테이블

클러스터 테이블은 동일한 클러스터 키 값을 가진 여러 테이블 레코드를 물리적으로 가까운 위치에 저장하는 구조다.

#### 인덱스 클러스터

클러스터 키 값이 같은 레코드를 하나 이상의 데이터 블록에 모아서 저장한다.

- 한 블록에 모두 저장할 수 없다면 여러 블록에 나누어 저장하고 클러스터 체인으로 연결한다.
- 일반 인덱스는 인덱스 키와 테이블 레코드가 1:1에 가까운 대응 관계를 갖는다.
- 클러스터 인덱스는 하나의 클러스터 키 값에 해당하는 데이터 블록을 가리키므로 1:M 관계를 갖는다.

**일반 인덱스와 클러스터 인덱스의 차이**

- 일반 인덱스: 인덱스 엔트리가 개별 테이블 레코드의 ROWID를 가리킨다.
- 클러스터 인덱스: 인덱스 엔트리가 해당 클러스터 키 값의 데이터가 저장된 첫 번째 블록을 가리킨다.

따라서 클러스터 인덱스를 통해 특정 키 값을 찾으면 해당 데이터 블록에 접근한 뒤, 클러스터 체인을 따라 같은 키 값을 가진 레코드를 탐색할 수 있다.

클러스터 키 값에 대한 접근은 인덱스를 통해 시작하고, 클러스터 내부의 데이터는 블록을 따라 탐색하므로 개별 레코드마다 별도의 랜덤 액세스를 수행하는 비용을 줄일 수 있다.

**생성 순서**

1. 클러스터 생성
2. 클러스터 인덱스 생성
3. 클러스터 테이블 생성

#### 해시 클러스터

인덱스를 사용하지 않고 해시 알고리즘을 이용해 클러스터를 찾아가는 방식이다.

- 클러스터 키 값을 해시 함수에 입력해 데이터가 저장된 위치를 찾는다.
- 별도의 클러스터 인덱스를 탐색하지 않아도 된다.
- 클러스터 키 값으로 동등 조건 조회를 수행하는 경우 유리하다.
- 범위 검색이나 정렬된 순서로 조회하는 경우에는 적합하지 않을 수 있다.

**생성 순서**

1. 클러스터 생성
2. 클러스터 테이블 생성

## 3.2 부분범위 처리 활용

### 부분범위 처리

DBMS는 조회 결과 전체를 한 번에 클라이언트로 전송하지 않고, 일정한 단위로 나누어 전송한다.

**예시: DBeaver에서 5,000건 조회**

조회 결과가 5,000건이더라도 화면에 처음부터 전체 데이터가 표시되는 것은 아니다.

- 최초 조회: 기본 설정된 200건 표시
- 스크롤하여 추가 조회: 설정된 Fetch Size만큼 추가로 가져옴
- 이후에도 필요한 시점에 추가 Fetch Call 발생

예를 들어 `200건 + 20건 + 20건` 이런 식으로

**동작 흐름**

1. 클라이언트가 SQL 실행을 요청한다.
2. DBMS가 데이터를 처리하고 일정량을 전송한다.
3. 전송이 끝나면 서버 프로세스는 CPU 반납하고 대기큐에서 다음 Fetch Call을 기다린다.
4. 클라이언트에서 추가 Fetch Call이 들어오면 이어서 데이터를 처리하고 전송한다.

### 정렬 조건이 있을 때의 부분범위 처리

- 정렬 조건이 있으면 전체 데이터를 다~ 읽고 정렬까지 다 하고나서 전송하기 시작함 -> 전체범위처리.. 
- 인덱스는 정렬된 상태를 유지하기 때문에 부분범위 처리 가능.

### Array Size와 Fetch Call

데이터 전송량에 따라 Array Size를 조절하면 Fetch Call 횟수를 줄일 수 있다.

- 대량 데이터를 반복적으로 가져오는 프로그램: Array Size를 늘리면 Fetch Call 횟수를 줄일 수 있다.
- 일부 데이터만 화면에 보여주는 프로그램: Array Size를 작게 설정하면 불필요한 데이터 전송을 줄일 수 있다.

**Array Size 조절 시 고려사항**

| 구분 | Array Size 크게 설정 | Array Size 작게 설정 |
|---|---|---|
| Fetch Call 횟수 | 감소 | 증가 |
| 한 번에 전송하는 데이터 | 많음 | 적음 |
| 메모리 사용량 | 증가 가능 | 상대적으로 적음 |
| 적합한 상황 | 대량 데이터 처리 | 일부 데이터만 조회 |

Array Size를 늘린다고 전체 조회 데이터가 줄어드는 것은 아니다. 전체 결과가 동일하다면 총 데이터 전송량은 같고, 전송 횟수와 한 번에 처리하는 양이 달라지는 것이다.

### OLTP 환경에서 부분범위 처리에 의한 성능 개선

온라인 프로그램에서도 대량의 데이터를 조회하는 상황이 발생할 수 있음.

**예시**
- 게시판 목록
- 입출금 거래 내역

화면에서 필요한 정렬 순서를 결정 -> 인덱스 구성 ->소트연산 생략이 되니까 부분범위 처리

**부분범위 처리의 핵심은 일부 데이터만 반환한 뒤 처리를 "멈출 수 있는가"이다.**

### 배치 I/O (Batch I/O)

인덱스를 통해 테이블에 접근할 때 발생하는 랜덤 I/O를 줄이기 위한 최적화 기법이다.

**배치 I/O의 동작 방식**

- 테이블 블록을 읽어야 할 때마다 즉시 디스크 I/O를 수행하지 않는다.
- 여러 ROWID를 일정량 모아둔다.
- 해당 ROWID들이 가리키는 테이블 블록을 모아서 처리한다.
- 가능하면 블록 접근 순서를 조정해 디스크 I/O 효율을 높인다.

즉, 개별적으로 여러 번 접근하는 대신 블록을 모아서 처리하여 랜덤 I/O 비용을 줄이는 방식이다.

**※주의 데이터 정렬 순서 보장안됨**

따라서 인덱스 순서만으로 `ORDER BY`를 만족할 수 있었던 경우에도 배치 I/O가 적용되면 정렬 순서를 보장하기 위한 별도의 Sort 연산이 필요할 수 있다.

반대로 정렬 순서를 보장할 필요가 없는 쿼리에서는 배치 I/O를 활용해 성능을 개선할 수 있다.

#### 배치 I/O가 활용될 수 있는 쿼리 예시 (옵티마이저가 배치 I/O 사용함)

**① 인덱스 컬럼에 없어서 정렬 연산을 생략할 수 없는 경우**

```sql
SELECT *
FROM EMP
WHERE DEPT_NO = 10
ORDER BY SALARY DESC;
```
- 인덱스 순서가 ORDER BY를 만족하지 않으므로 테이블 블록 접근 순서를 조정하는 배치 I/O를 활용할 수 있다.

**② ORDER BY가 없는 경우**

```sql
SELECT EMP_NM, SALARY
FROM EMP
WHERE DEPT_NO = 10;
```
- 정렬 순서를 보장할 필요가 없으므로 테이블 블록 접근 순서를 조정할 수 있다.

#### 애플리케이션 커서와 공유 커서 비교 (이부분은 지피티 사용이라 이해 못함)

| 구분 | 애플리케이션 커서 | 공유 커서 |
|---|---|---|
| 위치 | 애플리케이션 / 세션 측 | Oracle Shared Pool |
| 역할 | SQL 실행 및 결과 Fetch 관리 | SQL 파싱 정보 및 실행 계획 재사용 |
| 주요 개념 | Execute, Fetch, Close | Parse, Library Cache, Cursor |
| 관련 요소 | JDBC PreparedStatement, ResultSet | Parent Cursor, Child Cursor |

두 커서는 서로 다른 개념이지만 SQL 실행 과정에서 함께 연결되어 동작한다.

**전체 흐름**

1. 애플리케이션이 SQL 실행을 요청한다.
2. Oracle이 Library Cache에서 재사용할 공유 커서를 확인한다.
3. 기존 공유 커서를 사용할 수 있으면 재사용하고, 없으면 파싱 및 실행 계획 생성 등을 수행한다.
4. SQL을 실행하고 결과 집합을 준비한다.
5. 애플리케이션이 Fetch Call을 통해 결과를 가져온다.
6. 필요한 데이터를 모두 읽으면 커서를 닫는다.

## 3.3 인덱스 스캔 효율화

### 인덱스 탐색 구조

헷갈린 부분... 
- 일반 레코드가 가리키는 블록: 자신의 키 값 이상인 범위를 담당한다.
- LMC가 가리키는 블록: 첫 번째 키 값보다 작은 범위를 담당한다.

| 구분 | 키 값 | 하위 블록 |
|---|---:|---|
| LMC | - | 블록 A |
| 레코드 1 | 30 | 블록 B |
| 레코드 2 | 60 | 블록 C |
| 레코드 3 | 90 | 블록 D |

각 하위 블록이 담당하는 범위는 다음과 같다.

- LMC → 30보다 작은 키 값
- 30을 가리키는 주소 → 30 이상 60 미만
- 60을 가리키는 주소 → 60 이상 90 미만
- 90을 가리키는 주소 → 90 이상

즉, **일반 레코드의 키 값은 해당 하위 블록이 담당하는 범위의 시작점이고, LMC는 첫 번째 키 값보다 작은 범위를 담당한다.**

### 인덱스 스캔 시작점과 끝점

스캔 시작점을 찾는 과정 -> 수직적탐색
리프 블록에 도달한 뒤, 조건절에 부합하는 첫 번째 인덱스 레코드를 발견한 지점 -> 스캔시작점

조건절에 따라서 얼마나 스캔량을 줄이는데 기여했는지... 이런것도 문제로 나올 것 같기도.. 
수직적 탐색과정에 참여한다 (스캔 시작점을 결정지음)
스캔을 멈추는 거에 대한 역할을 했는가.. 


### 인덱스 선행 컬럼과 스캔 효율

인덱스 선행컬럼이 조건절에 없거나 '=' 조건이 아니면 인덱스 스캔 과정에 비효율이 발생함.

- 선두 컬럼: 인덱스 구성상 가장 앞에 있는 컬럼
- 선행 컬럼: 특정 컬럼보다 상대적으로 앞에 위치한 컬럼


인덱스 액세스 조건 : 인덱스 스캔 범위를 결정하는 조건절. 수직적 탐색으로 시작점을 리프 블록을 스캔하면서 끝점을 결정하는데 영향을 미침.
인덱스 필터 조건 : 테이블로 액세스할지를 결정하는 조건절/ 테이블 액세스 단계에서 처리되는 조건절은 모두~ 필터 조건 
테이블 필터 조건 : 쿼리 수행 다음 단계로 전달하거나 최종 결과집합에 포함할지를 결정.


여러 조건절이 존재할 떄 선행 컬럼이 모두 '=' 조건인 상태에서 첫번째 나타나는 범위검색 조건까지만 만족하는 인덱스 레코드는 모두 연속해서 모여있고 그 이하 조건까지 만족하는 레코드는 비교 연산자 종류에 상관없이 흩어져있다는 규칙.. 


### 인덱스 액세스 조건으로 활용하기 어려운 경우

다음과 같은 조건은 인덱스 액세스 조건으로 사용하기 어렵다.

- 좌변 컬럼을 가공한 조건절
- 왼쪽 또는 양쪽에 '%'를 사용한 LIKE 조건절
- 동일한 컬럼에 조건절이 여러 개 존재할 때 액세스 조건으로 선택되지 못한 조건절
- OR Expansion 또는 INLIST ITERATOR로 변환되지 않은 OR 또는 IN 조건절

예시:

```sql
-- 컬럼 가공
WHERE SUBSTR(EMP_NO, 1, 3) = '100'

-- 왼쪽에 %
WHERE EMP_NM LIKE '%홍'

-- 양쪽에 %
WHERE EMP_NM LIKE '%홍%'

-- OR 조건
WHERE DEPT_NO = 10
OR DEPT_NO = 20
```

컬럼을 가공하면 원래 컬럼에 생성한 일반 인덱스의 정렬 구조를 그대로 활용하기 어렵다.

단, 함수 기반 인덱스나 별도의 쿼리 변환을 통해 인덱스 액세스 조건으로 활용할 수 있는 경우도 있다.

**One-Plus 스캔:조건을 만족하는 레코드가 더 없음을 확인하기 위한 스캔.**


#### BETWEEN을 IN-LIST로 전환

in 절로 변경했을 때 인덱스 수직적 탐색이 n번 발생하여 실행계획에 INLIST ITERATOR가 찍히는 것을 볼 수 있음 
옵티마이저가 IN절을 '='조건으로  UNION ALL 해서 실행하게되는거지. 
IN-LIST 항목 개수가 늘어나게 된다면 리프블록을 많이 스캔하는 between 비효율보다 인덱스 수직탐색 하는 것이 더 비효율적이 될 수 있음.
인덱스 스캔 과정에서 선택되는 레코드들이 서로 멀리 떨어져있을 때 유용함

선두 컬럼이 between 이어서 나머지 검색 조건을 만족하는 데이터가 서로 멀리 떨어져있을때 위력이 나타남...

인덱스 구성 컬럼 중 몇 번째 컬럼까지 액세스 조건으로 활용할지 지정하는 힌트다.

인덱스 컬럼을 함수로 가공하면 일반 인덱스의 정렬 구조를 활용하기 어려워진다.

### 9. BETWEEN과 LIKE 비교

예시 
1)
WHERE 판매월 BETWEEN '202601' AND '202612'
AND 판매구분 = 'B'

2)
WHERE 판매월 LIKE '2026%'
AND 판매구분 = 'B'

2) 의 경우 판매월이 '202600' 이 있을 수도 있기 때문에 판매구분 = 'B' 로 갈 수가 없음 (B가 아닌 다른 범위의 데이터도 보고나서 찾)


### 10. 옵션 조건 처리

검색 조건 중 사용자가 값을 입력할 수도 있고 입력하지 않을 수도 있는 조건을 옵션 조건이라고 한다.

예를 들어 고객ID를 입력하면 해당 고객만 조회하고, 입력하지 않으면 전체 고객을 조회하는 경우다.

```sql
WHERE 고객ID LIKE :cust_id || '%'
AND 거래일자 BETWEEN :from_dt AND :to_dt;
```

- 고객ID가 입력되면 해당 고객ID로 시작하는 데이터 조회
- 고객ID가 입력되지 않으면 전체 고객 범위 조회

이때 고객ID의 조건 유무에 따라 인덱스 액세스 조건이 달라질 수 있다.

값이 입력되면 고객ID 조건을 이용해 스캔 범위를 줄일 수 있지만, 값이 입력되지 않으면 해당 조건의 변별력이 사라진다.

이러한 차이 때문에 옵션 조건은 값이 들어오는 경우와 들어오지 않는 경우의 성능을 모두 확인해야 한다.

#### 옵션 조건에 OR 사용

- 인덱스 액세스 조건으로 사용 불가 
- 인덱스 필터 조건으로도 사용 불가 
- 테이블 필터 조건으로만 사용가능 
- 인덱스 구성 컬럼 중 하나 이상이 NOT NULL 컬럼이면 18C부터 인덱스 필터 조건으로 사용가능 

**NULL 허용 여부와 인덱스의 관계**

Oracle의 일반 B-tree 인덱스는 인덱스 구성 컬럼이 모두 NULL인 행을 저장하지 않는다.

따라서 단일 컬럼 인덱스의 컬럼이 NULL인 행은 인덱스에 존재하지 않는다.

하지만 인덱스 구성 컬럼 중 하나라도 NOT NULL인 컬럼이 있으면 해당 행도 인덱스에 저장될 수 있다.


#### LIKE / BETWEEN 옵션 조건

변별력이 좋은 필수 조건이 존재하면 얘네 활용해도 그렇게 비효율 아님
근데 필수 조건이 변별력이 떨어지면 TABLE FULL SCAN이 나은데 옵티마이저는 이 범위검색 조건에 해당하는 컬럼이 들어올거를 가정하기 때문에 INDEX RANGE SCAN으로 선택해버림...;;; 
없었을 때의 성능이 너무 안좋다 

이때 고객ID가 NULL인 행은 조회되지 않는다.

**왜 NULL인 행이 누락될까?**

SQL에서 NULL은 일반적인 값이 아니므로 비교 결과가 TRUE 또는 FALSE가 아니라 UNKNOWN이 된다.
WHERE 절은 TRUE인 행만 반환하므로 NULL인 행은 결과에서 제외된다.


**옵션 조건 처리 시 점검할 항목**

1. 인덱스 선두 컬럼인지 확인
2. NULL 허용 컬럼인지 확인
3. 숫자형 컬럼인지 확인
4. 가변 길이 컬럼인지 확인

① 인덱스 선두 컬럼

```sql
WHERE 고객ID LIKE :cust_id || '%'
AND 거래일자 BETWEEN :from_dt AND :to_dt;
```

고객ID가 인덱스 선두 컬럼이면 고객ID 값이 입력되지 않았을 때 인덱스 활용도가 떨어질 수 있다.

이때 인덱스를 다음과 같이 변경하는 방안을 고려할 수 있다.

```sql
(거래일자, 고객ID)
```

고객ID 조건을 활용하지 못하는 경우에도 거래일자 조건으로 범위를 좁힐 수 있다.

다만 고객ID가 입력되는 경우에는 기존 인덱스보다 불리할 수 있으므로 두 상황을 비교해야 한다.

② NULL 허용 컬럼

```sql
WHERE 고객ID LIKE '%'
```

고객ID가 NULL인 행은 조회되지 않는다.

옵션 조건을 생략한 것처럼 생각하고 사용하면 결과가 누락될 수 있으므로 주의해야 한다.

③ 숫자형 컬럼

```sql
WHERE EMP_NO LIKE :emp_no || '%'
```

숫자형 컬럼에 LIKE를 사용하면 문자열 비교를 위해 형변환이 필요하다.

이 과정에서 일반 숫자형 인덱스를 액세스 조건으로 활용하지 못할 수 있다.

숫자형 컬럼이라면 숫자형 비교 조건을 사용하는 것이 좋다.

④ 가변 길이 컬럼

이름과 같이 길이가 일정하지 않은 문자열은 접두어 검색 시 예상하지 못한 결과가 나올 수 있다.

예를 들어 다음 조건을 생각해 보자.

```sql
WHERE EMP_NM LIKE '허설%'
```

조회 결과에는 다음 데이터가 모두 포함될 수 있다.

- 허설
- 허설설
- 허설이

정확히 두 글자만 조회하려면 길이 조건을 추가해야 한다.

```sql
WHERE EMP_NM LIKE '허설%'
AND LENGTH(EMP_NM) = 2;
```

### UNION ALL을 활용한 옵션 조건 처리

옵션 컬럼이 NULL일 때와 값이 있을 때를 각각 분리해 작성하는 방식이다.

```sql
SELECT *
FROM CUSTOMER
WHERE :cust_id IS NULL

UNION ALL

SELECT *
FROM CUSTOMER
WHERE :cust_id IS NOT NULL
AND CUSTOMER_ID = :cust_id;
```

**장점**

- 옵션 조건 컬럼을 인덱스 액세스 조건으로 활용할 수 있다.
- NULL 여부에 따라 실행할 조건을 명확하게 분리할 수 있다.
- NULL 허용 컬럼에도 적용할 수 있다.

**단점**

- SQL이 길어진다.
- 옵션 조건이 많아질수록 쿼리 관리가 복잡해진다.

두 분기는 서로 배타적이므로 중복 결과가 발생하지 않는다.

### NVL / DECODE 함수를 활용한 옵션 조건 처리

인덱스 컬럼 가공을 했는데도 OR EXPANSION 쿼리 변환이 되서 인덱스 사용이 가능하다~
UNION ALL 방식과 동일하게 실행계획이 나옴 
대신 NULL 허용 컬럼은 안됨 

여러개 사용하면 변별력 가장 좋은컬럼 기준으로 한번만 OR EXPANSION일어남 
이 변환 기준이 되지 않으면 걍 필터 조건으로 되는거임...;; 
다이나믹 SQL을 사용할때는 바인드 변수를 잘 활용하자..


옵션 조건이 많고 실행 계획의 차이가 크다면 Dynamic SQL을 활용하는 방법도 고려할 수 있다.

Dynamic SQL을 사용할 때는 바인드 변수를 적절히 활용해 SQL 재사용성을 확보하는 것이 좋다.

### PL/SQL 함수가 느려지는 이유

인터프리터 언어여서 
호출 시 마다 컨텍스트 스위칭 되서 
내장 SQL에 대한 Recursive call 발생해서

따라서 가능하면 SQL 자체로 처리하는 것이 유리하다.

다만 업무 로직이 복잡해 PL/SQL 함수를 사용해야 한다면 다음과 같이 접근한다.

- 함수 호출 횟수를 줄인다.
- 인덱스 액세스 조건을 활용해 대상 행 수를 줄인다.
- 함수 기반 인덱스를 활용할 수 있는지 검토한다.

### 함수 기반 인덱스(Function-Based Index)

함수 기반 인덱스는 컬럼에 함수를 적용한 결과를 인덱스로 구성하는 방식이다.
함수를 사용하는 컬럼도 인덱스로 구성을 하면 액세스조건으로 사용되서 단 한번 호출 됨.
