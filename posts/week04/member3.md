## 3.1 테이블 액세스 최소화

### 테이블 랜덤 액세스

인덱스를 사용하더라도 대량의 데이터를 조회하면 테이블 풀 스캔보다 오히려 느려질 수 있다.

- SQL에서 참조하는 컬럼을 인덱스가 모두 포함하지 않는다면, 인덱스 스캔 후 테이블을 추가로 액세스해야 한다.
- 실행 계획에는 `TABLE ACCESS BY INDEX ROWID`로 표시.

#### ROWID와 테이블 액세스

ROWID는 테이블 레코드의 물리적 위치를 식별하기 위한 논리적 주소 정보다.

- 예시 : ROWID는 우편번호 / 포인터는 전화번호 같은 것.
- 인덱스 리프 블록에서 ROWID를 확인 -> DBA 정보를 얻음 -> 버퍼 캐시 있없 찾기 -> DBA 이용해서 해시함수 해시체인 찾음 -> 버퍼 헤더 찾음 -> 헤더가 가리키는 버퍼 블록..
- 디스크 I/O 필요하면 디스크 갔다가 버퍼 캐시에 넣고 위의 과정.. 

#### 인덱스 스캔과 풀 스캔의 블록 탐색 차이

- 인덱스 스캔: 리프 블록에서 ROWID를 얻고, ROWID를 통해 테이블 블록의 DBA를 확인한다.
- 테이블 풀 스캔: 세그먼트의 익스텐트 정보를 이용해 읽을 데이터 블록의 위치를 파악한다.

이러한 탐색 과정에서 동시 액세스가 많아지면 캐시 버퍼 체인 래치(Latch), 버퍼 락(Buffer Lock) 등의 경합이 발생할 수 있다.


### 인덱스 클러스터링 팩터(Clustering Factor)

클러스터링 팩터는 **인덱스의 정렬 순서와 테이블 데이터의 물리적 저장 순서가 얼마나 유사한지**를 나타내는 지표다.

- 같은 인덱스 키 순서로 데이터를 조회했을 때 테이블 블록이 물리적으로 모여 있으면 클러스터링 팩터가 좋다. -> 찾는 속도가 빠름

**클러스터링 팩터의 효과**

- 클러스터링 팩터가 좋으면 테이블 액세스 횟수에 비해 실제 블록 I/O가 적게 발생할 수 있다.
- 인덱스 스캔 중 직전에 읽은 테이블 블록과 다음에 읽을 테이블 블록이 같다면, 포인터를 해지하지 않고 유지하는데 이 관련 기법 버퍼 피닝
- 그걸 이용해서 해당 블록을 다시 찾는 일부 논리적 탐색 과정을 생략할 수 있음.
- 다음 인덱스 레코드가 직전에 읽은 것과 동일한 테이블 블록을 가리키면 버퍼 탐색 과정을 줄일 수 있다.
- 클러스터링 팩터가 나쁘면 인덱스 레코드마다 서로 다른 테이블 블록을 찾아가는 경우가 많아진다.

### 인덱스 손익분기점

인덱스 손익분기점은 인덱스 레인지 스캔이 테이블 풀 스캔보다 느려지는 지점.

| 구분 | 테이블 풀 스캔 | 인덱스 레인지 스캔 |
|---|---|---|
| 접근 방식 | 시퀀셜 액세스 | 인덱스 범위 탐색 및 테이블 랜덤 액세스 |
| I/O 특성 | 멀티블록 I/O 활용 | 싱글블록 I/O가 자주 발생 |

### 온라인 프로그램 튜닝 VS 배치 프로그램 튜닝

| 구분 | 온라인 프로그램 | 배치 프로그램 |
|---|---|---|
| 데이터 처리 | 소량의 데이터 | 대량의 데이터 |
| 주요 튜닝 방향 | 응답 시간 최소화 | 전체 처리 시간 최소화 |
| 대표적인 방식 | NL 조인, 인덱스 활용 | 해시 조인, 풀 스캔 |
| 데이터 액세스 | 필요한 데이터만 빠르게 조회 | 전체 범위 처리 고려 |

**배치 프로그램에서는 파티션 활용 전략도 중요하다.**

테이블 파티셔닝은 FULL SCAN을 빠르게 처리하기 위함. 
그래서 파티셔닝 된 테이블에 인덱스를 쓰더라도.. 쿼리 성능이 그닥.. 

### Covered 쿼리와 INCLUDE 인덱스

#### Covered 쿼리 / Covered Index

- Covered 쿼리: SQL에서 필요한 컬럼을 인덱스만으로 모두 처리할 수 있는 쿼리
- Covered Index: 해당 쿼리에 필요한 컬럼을 모두 포함하고 있는 인덱스

인덱스만으로 필요한 데이터를 처리할 수 있으므로 테이블 랜덤 액세스를 줄일 수 있다.

#### INCLUDE 인덱스

인덱스 키 컬럼 외에 추가 컬럼을 리프 블록에 저장하는 방식이다.

- 인덱스 키 컬럼: 루트·브랜치·리프 블록에 저장되며 인덱스 탐색에 사용된다.
- INCLUDE 컬럼: 리프 블록에만 저장되며 인덱스 탐색 조건(수직적탐색)에는 사용되지 않는다.
- INCLUDE 컬럼은 테이블 랜덤 액세스를 줄이는 용도로 활용한다.
- INCLUDE 컬럼은 인덱스 키가 아니므로 해당 컬럼을 이용해 소트 연산을 생략할 수는 없다.

### 인덱스 구조 테이블(IOT: Index-Organized Table)

테이블 자체를 인덱스 구조로 저장하는 방식.

- 일반 테이블은 데이터가 힙(Heap) 구조로 저장되고, 인덱스는 별도로 존재한다.
- IOT는 테이블 데이터를 인덱스 구조의 리프 블록에 저장한다.
- 따라서 일반 테이블처럼 ROWID를 이용해 별도의 테이블 블록을 찾아갈 필요가 없다.
- 시퀀셜 방식으로 데이터를 액세스 하기 때문에 범위 탐색할 때 유리 

**일반 테이블과 IOT 비교**

| 구분 | 일반 테이블 | IOT |
|---|---|---|
| 데이터 저장 | 힙 구조 | 인덱스 구조 |
| 인덱스 리프 | ROWID 저장 | 실제 테이블 데이터 저장 |
| 데이터 조회 | 인덱스 → ROWID → 테이블 | 인덱스에서 데이터 직접 조회 |

생성 시 다음과 같이 지정한다.

```sql
CREATE TABLE EMP (
    EMP_NO NUMBER PRIMARY KEY,
    EMP_NM VARCHAR2(100)
)
ORGANIZATION INDEX;
```

IOT는 데이터를 인덱스 구조에 저장함으로써 인덱스 키 기준의 클러스터링 효과를 얻는 방법 중 하나다.

### 클러스터 테이블

클러스터 테이블은 동일한 클러스터 키 값을 가진 여러 테이블 레코드를 물리적으로 가까운 위치에 저장하는 구조다.

#### 인덱스 클러스터

클러스터 키 값이 같은 레코드를 하나 이상의 데이터 블록에 모아서 저장한다.

- 한 블록에 모두 저장할 수 없다면 여러 블록에 나누어 저장하고 클러스터 체인으로 연결한다.
- 일반 인덱스는 인덱스 키와 테이블 레코드가 1:1에 가까운 대응 관계를 갖는다.
- 클러스터 인덱스는 하나의 클러스터 키 값에 해당하는 데이터 블록을 가리키므로 1:M 관계를 갖는다.

**일반 인덱스와 클러스터 인덱스의 차이**

- 일반 인덱스: 인덱스 엔트리가 개별 테이블 레코드의 ROWID를 가리킨다.
- 클러스터 인덱스: 인덱스 엔트리가 해당 클러스터 키 값의 데이터가 저장된 첫 번째 블록을 가리킨다.

따라서 클러스터 인덱스를 통해 특정 키 값을 찾으면 해당 데이터 블록에 접근한 뒤, 클러스터 체인을 따라 같은 키 값을 가진 레코드를 탐색할 수 있다.

클러스터 키 값에 대한 접근은 인덱스를 통해 시작하고, 클러스터 내부의 데이터는 블록을 따라 탐색하므로 개별 레코드마다 별도의 랜덤 액세스를 수행하는 비용을 줄일 수 있다.

**생성 순서**

1. 클러스터 생성
2. 클러스터 인덱스 생성
3. 클러스터 테이블 생성

#### 7.2 해시 클러스터

인덱스를 사용하지 않고 해시 알고리즘을 이용해 클러스터를 찾아가는 방식이다.

- 클러스터 키 값을 해시 함수에 입력해 데이터가 저장된 위치를 찾는다.
- 별도의 클러스터 인덱스를 탐색하지 않아도 된다.
- 클러스터 키 값으로 동등 조건 조회를 수행하는 경우 유리하다.
- 범위 검색이나 정렬된 순서로 조회하는 경우에는 적합하지 않을 수 있다.

**생성 순서**

1. 클러스터 생성
2. 클러스터 테이블 생성

- **CR**: 실행 통계에서 `CR`은 일반적으로 Consistent Read를 의미한다. Oracle의 일관된 읽기를 위한 논리적 블록 읽기이며, `Consistent Gets`로 집계된다. `Current Gets`와 구분해서 이해하면 좋다.
