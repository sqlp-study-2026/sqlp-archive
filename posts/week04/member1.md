# 3장

## 친절한 SQL 튜닝 3.3-3.4
### 1. 인덱스 탐색
인덱스 선행 컬럼이 조건절에 없거나 '=' 조건이 아니면 인덱스 스캔 과정에서 비효율 발생

- 인덱스 액세스 조건: 인덱스 스캔 범위를 결정하는 조건절
인덱스 수직적 탐색을 통해 스캔 시작점을 결정하는 데 영향을 미치고, 인덱스 리프 블록을 스캔하다가 어디서 멈출지를 결정하는 데에 영향을 미치는 조건절
- 인덱스 필터 조건: 테이블로 액세스할지를 결정하는 조건절
- 테이블 필터 조건: 쿼리 수행 다음 단계로 전달하거나 최종 결과집합에 포함할지를 결정(테이블에 접근한 후 조건을 검사)

### 2. 인덱스 스캔 효율화
#### 비교 연산자 종류와 컬럼 순서에 따른 군집성
선행 컬럼이 모두 '=' 조건인 상태에서 첫번째 나타나는 범위검색 조건까지만 만족하는 인덱스 레코드는 모두 연속해서 모여 있지만, 그 이하 조건까지 만족하는 레코드는 비교 연산자 종류에 상관 없이 흩어짐.
- 선행 컬럼이 모두 '=' 조건인 상태에서 처음 나타나는 범위검색 조건은 인덱스 액세스 조건(= 인덱스 스캔 범위 결정)
- 나머지 인덱스 컬럼 조건은 모두 인덱스 필터 조건

#### 인덱스 선행 컬럼이 등치(=) 조건이 아닐 때 생기는 비효율
인덱스 컬럼을 조건절에 모두 등치(=)조건으로 사용하면, 리프 블록을 스캔하면서 읽은 레코드가 모두 테이블 액세스로 이어져 인덱스 스캔 단계에서의 비효율이 없음.<br/>
(필요한 인덱스 범위만 스캔하고 멈출 수 있는 것은, 조건을 만족하는 레코드가 모여있기 때문)<br/>
반면, 인덱스 선행 컬럼이 조건절에 없거나 범위검색 조건(부등호, BETWEEN, LIKE)이면, 인덱스 스캔 시 비효율 발생.

#### BEWEEN을 IN-List로 전환
- 실행계획에 'INLIST ITERATOR' 표시
- IN-List Iterator 방식: IN 조건을 여러 개의 '=' 조건으로 나누어 인덱스를 반복 탐색하는 방식으로, 후행 컬럼까지 인덱스 액세스 조건으로 활용할 수 있다.
- IN-List 개수만큼 UNION ALL 브랜치 생성되고 각 브랜치마다 '=' 조건으로 검색.
- IN-List 개수만큼 수직탐색
- 다만, BETWEEN 조건 때문에 리프 블록을 많이 스캔하는 비효율보다 IN-List 개수만큼 브랜치블록을 반복 탐색하는 비효율이 더 클 수 있음.
- IN 값의 개수가 적지 않다면, 선행 컬럼의 NDV가 낮을수록 유리

#### IN 조건 활용
- IN 조건이 '='이 됟려면 IN-List Iterator 방식으로 사용해야 하며, 그렇지 않은 경우에 IN 조건은 필터조건.
- num_index_keys 힌트를 사용하여 인덱스의 액세스 조건으로 사용할 컬럼 지정 가능.

#### BETWEEN과 LIKE 스캔 범위 비교
가능한 BETWEEN을 사용하길

#### 범위검색 조건을 남용할 때 생기는 비효율
- 범위조건(Like등)을 사용하면 해당 조건이 액세스 조건이 아닌 필터조건으로 바뀌어 비효율 발생 가능
- 인덱스 선두 컬럼에 대한 옵션 조건에 OR 조건을 사용하면 안됨.<br/>
단, 인덱스에 포함되지 않은 컬럼 조건은 어차피 필터링 역할이므로 OR가 성능에 영향을 미치지 않음.
	- OR 조건 사용 시, 인덱스 액세스/필터 조건 사용 불가(테이블 필터 조건으로만 사용 가능)
- 필수 조건 컬럼을 선두에 두어 액세스로 사용하면, LIKE/BETWEEN이 인덱스 필터 조건이 어도 좋은 성능 가능
	- 인덱스 선두 컬럼을 LIKE/BETWEEN으로 처리 지양
    - NULL 허용 컬럼도 LIKE/BETWEEN으로 처리 지양
    - 숫자형이면서 인덱스 액세스 조건으로 사용 가능한 컬럼은 LIKE 지양
    - LIKE 조건을 사용하려면 컬럼 값 길이가 고정적이어야 함.
- UNION ALL  활용
- NULL이 불가한 컬럼에서는 NVL, DECODE 함수 사용하여 인덱스 액세스 조건으로 사용 가능

### 스캔 효율성에 기반한 판단 기준
- 인덱스 선두 컬럼을 조건절에 반드시 사용해야 함.
결합 인덱스를 구성할 때, 조건절에 항상 사용하거나 자주 사용하는 컬럼을 선정해야 함.
또한, 그렇게 선정한 컬럼 중 '=' 조건으로 자주 조회하는 컬럼을 앞쪽에 두어야 함.

### 그외 판단 기준
- 수행 빈도
	NL 조인 시, Inner 쪽 인덱스(우측)는 '=' 조건 컬럼을 선두에 두는 것이 중요하고, 될 수 있으면 테이블 액세스 없이 인덱스에서 필터링을 마치도록 구성
- 업무상 중요도
- 클러스터링 팩터
- 데이터량
- DML 부하
- 저장공간
- 인덱스 관리 비용 등

### 소트 연산 생략
조건절에 사용하지 않는 컬럼이어도 소트 연산을 생략할 목적으로 인덱스 구성에 포함시켜 성능 개선
'='이 아닌 조건절 컬럼들은 반드시 ORDER BY 컬럼보다 뒤쪽에 두어야 소트 연산 생략 가능
소트 연산 생략을 위해서는 IN 조건절을 인덱스 액세스 조건으로 사용해서는 안됨.
- '=' 연산자로 사용한 조건절 컬럼 선정
- ORDER BY 절에 기술한 컬럼 추가
- '=' 연산자가 아닌 조건절 컬럼은 데이터 분포를 고려해 추가 여부 결정

### 결합 인덱스 선택도
- 선택도=전체 레코드 중에서 조건절에 의해 선택되는 레코드 비율
- 인덱스 선택도=인덱스 컬럼을 모두 '='으로 조회할 때 평균적으로 선택되는 비율
선택도가 높음(카디널리티가 높은) 인덱스는 테이블 액세스가 많이 발생하여 효용가치 없음.
