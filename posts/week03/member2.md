## 3.1 테이블 액세스 최소화
SQL에 사용된 컬럼이 인덱스에 포함되어있는 컬럼들이 아니라면 ROWID를 이용한 테이블 액세스는 무조건 일어난다.
인덱스를 잘 타도 느려지는 이유는 테이블 랜덤 액세스가 원인이며, 1개의 테이블 레코드를 읽기위해 루트 블록 ->
브랜치 블록 -> 리프 블록 -> 테이블 블록 -> 테이블 레코드 순으로 복잡한 순서를 거치며 접근한다. 절대 단순한 과정이 아니며,
고비용임을 알아야한다. 또한, 블록들이 버퍼 캐시에 다 있으면 좋겠지만, 테이블이 크다면 블록들이 밀려나 있을 확률이 높다.
또한, CF가 나쁘면 테이블 랜덤 액새스 비용이 증가한다. 앞서 말한 2가지 경우에는 TABLE FULL SCAN을 사용하는 것이 더 효율적이다.

테이블 랜덤 액세스를 최소화 하기 위한 방법은 다음과 같다.

### 1. 인덱스 컬럼 추가
운영 중에 사용하고 있는 쿼리에 인덱스 컬럼을 변경하기엔 다소 리스크가 존재한다.
그럴 경우는 기존 인덱스에 인덱스 컬럼을 추가하여 테이블 랜덤 액세스 횟수를 줄일 수 있다.
조건절에 A,B 컬럼이 있을 경우에 A에만 인덱스가 있고 B는 없다면 A로만 얻은 ROWID 만큼 B 값으로 테이블에서
조건을 걸러내야 하기 때문에 이만큼 테이블 랜덤 액새스가 일어난다. 따라서,처음부터 A+B로 얻은 ROWID 값으로 테이블 레코드에 
접근할 수 있으면 테이블 액새스를 최소화 할 수 있기 때문이다.

즉, 불필요한 테이블 랜덤 액세스를 줄이는 거다.

### 2. 인덱스 구조 테이블(IOT)
테이블을 찾아가기 위한 하나의 인덱스 테이블이 아닌 처음부터 테이블 블록에 있어야 할 데이터를
인덱스 리프 블록에 모두 저장하고 있는 테이블이다.


### 3. 클러스터 테이블
클러스터 키 값이 같은 레코드를 한 블록에 모아서 저장하는 구조의 테이블이다.

IOT와 클러스터 테이블은 인위적으로 CF를 낮게 방식이나 IOT는 데이터를 정렬된 구조로 저장하지만
클러스터 테이블은 정렬된 구조를 보장하지 않는다.

## 3.2 부분범위 처리 활용
DBMS에서 읽은 전체 쿼리 결과 집합을 계속 사용자에게 전송하는 것이 아닌
사용자로부터 Fetch Call이 있을 때마다 일정량씩 나누어 전송하는 것을 뜻한다.

데이터를 전송하는 단위는 Array Size이며 JAVA에서 기본값은 10이다.
