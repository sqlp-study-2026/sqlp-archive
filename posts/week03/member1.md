#### 3.1-3.2

### 1. 테이블 랜덤 액세스
인덱스 ROWID는 테이블 레코드를 찾아가기 위한 논리적 주소.<br>
오라클의 경우, ROWID가 가지는 디스크 주소 정보(DBA)를 이용해 해시 알고리즘으로 버퍼 블록을 찾아감.<br>
I/O 성능을 높이려면 버퍼 캐시를 활용해야 함.<br>
버퍼 헤더는 같은 해시 체인에 연결되지만, 실제 데이터가 담긴 버퍼 블록은 매번 다른 위치에 캐시되고, 그 메모리 주소값을 버퍼 헤더가 가지고 있음.<br>
즉, 해싱 알고리즘으로 버퍼 헤더를 찾고, 거기서 얻은 포인터로 버퍼 블록을 찾음.<br>
ROWID가 가리키는 테이블 블록을 버퍼캐시에서 먼저 찾아보고 못 찾으면 디스크에서 블록을 읽음.<br>

### 2. 인덱스 클러스터링 팩터
클러스터링 팩터(CF)=특정 컬럼을 기준으로 같은 값을 갖는 데이터가 서로 모여있는 정도<br>
CF가 좋은 컬럼의 인덱스는 블록I/O가 적게 발생하여 검색 효율이 좋음.

### 3. 인덱스 손익분기점
인덱스 손익분기점=Index Range Scan이 Table Full Scan보다 느려지는 지점<br>
인덱스 ROWID를 이용한 테이블 액세스가 고비용이어서, 읽는 데이터가 많아지다보면 테이블 전체 스캔하는 것보다 느려질 수 있음. 인덱스 ROWID를 이용한  테이블 액세스 방식은 랜덥 액세스, Single Block I/O 방식이기 때문.<br>
- 온라인 프로그램 튜닝
소량 데이터를 다루기 때문에 인덱스를 효과적으로 사용해야 함.<br>
주로 인덱스를 이용한 NL 조인 방식 사용
- 배치 프로그램 튜닝
대량 데이터를 다루기 때문에 전체를 빠르게 처리하는 것에 집중.<br>
Full Scan과 해시 조인 유리<br>
또한, 파티션 활용 전략이 중요(테이블을 파티셔닝하는 이유는 Full Scan을 빠르게 처리하기 위함)

### 4. 인덱스의 랜덤 액세스 줄이기
- Covered 인덱스
인덱스만 읽어서 처리할 수 있도록 쿼리에 사용된 모든 컬럼을 인덱스에 추가
- IOT(Index-Organized Table) / 클러스터형 인덱스
인덱스 리프 블록에 ROWID가 아니라, 데이터를 저장<br>
인덱스 구조 테이블이기 때문에, 데이터 입력 시 정렬 상태를 유지하여 CF가 좋음.<br>
정렬되어 있기 때문에 시퀀셜 방식으로 액세스되어 범위 조회에도 유리
- 인덱스 클러스터 테이블
클러스터 키 값이 같은 레코드를 한 블록에 모아 저장<br>
B*Tree 인덱스 구조이지만, 해당 키 값을 저장하는 첫 데이터 블록을 가리킴. 즉, 클러스터 인덱스의 키 값은 항상 유니크.
- 해시 클러스터 테이블
인덱스를 사용하지 않고, 해시 알고리즘을 사용하여 클러스터를 찾아감.

### 5. 부분범위 처리
전체 쿼리 결과집합을 쉼 없이 연속적으로 전송하지 않고 사용자로부터 Fetch Call이 있을 때마다 일정량씩 나누어 전송하는 것

- Array Size = 데이터를 전송하는 단위
대량의 데이터를 받아야 할 경우, Array  Size를 크게 설정해야 Fetch Call 횟수를 줄일 수 있음.

- 정렬 조건이 추가되는 순간 전체범위처리
단, 정렬 컬럼이 선두인 인덱스가 있다면, 부분범위 처리 가능

### 6. 오라클 배치 I/O
읽는 블록마다 건건이 I/O Call을 발생시키는 비효율을 줄이기 위해 고안<br>
인덱스를 이용해 테이블을 액세스하다가 버퍼 캐시에서 블록을 찾지 못하면 일반적으로 디스크 블록을 바로 읽는데, 이 기능이 작동하면 테이블 블록에 대한 디스크 I/O Call을 미뤘다가 읽을 블록이 일정량 쌓이면 한꺼번에 처리<br>
단, 배치 I/O 기능이 작동하면 인덱스를 이용해서 출력하는 데이터 정렬 순서가 매번 다를 수 있음.

### 7. 핵심정리

인덱스 ROWID가 가리키는 테이블 블록을 버퍼캐시에서 먼저 찾아보고, 못 찾을 때만 디스크에서 블록을 읽음(버퍼캐시에 먼저 적재)

**3.1.7 클러스터 테이블 부분은 읽고 특성만 기억**
- 인덱스 클러스터 테이블
  클러스터 키 값이 같은 레코드를 한 블록에 모아서 저장<br>
  클러스터 인덱스의 키 값은 항상 유니크<br>
  클러스터 인덱스를 스캔하면서 값을 찾을 때는 랜덤 엑세스가 값 하나당 한번씩 발생하여 넓은 범위를 읽더라도 비효율이 없음.
- 해시 클러스터 테이블
  인덱스 사용하지 않고, 해시 알고리즘을 사용해 클러스터를 찾아감.

**76.p 의 ROWID의 구성과 인덱스 레코드 구성 복습**
- ROWID
  테이블 레코드를 가리키는 주소값<br>
  ROWID = 데이터 블록 주소 + 로우 번호 = (데이터 파일 번호 + 블록 번호) + 로우 번호
- 인덱스 레코드
  인덱스 키 값(정렬기준) + ROWID

### 8. 문제풀이
1-1 SQL 수행 구조 문제 풀이
#### 오라클
- 데이터베이스: 디스크에 저장된 데이터 집합(물리적인 OS 파일의 집합)
- 인스턴스: SGA 공유 메모리 영역과 이를 액세스하는 프로세스 집합
기본적으로 하나의 인스턴스가 하나의 데이터베이스를 액세스하지만, RAC(Real Application Cluster) 환경에서는 여러 인스턴스가 하나의 데이터베이스를 액세스 가능. 하나의 인스턴스가 여러 데이터베이스 액세스 불가.

#### 백그라운드 프로세스
- System Monitor(SMON): 장애가 발생한 시스템 재기동할 때 인스턴스 복구 수행, 임시 세그먼트와 익스텐트 모니터링
- Process Monitor(PMON): 이상이 생긴 프로세스가 사용하던 리소스 복구
- Database Writers(DBWn): 버퍼캐시에 있는 Dirty 버퍼를 데이터파일에 기록
- Log Writer(LGWR): 로그 버퍼 엔트리를 Redo 로그 파일에 기록
- Archiver(ARCn): 꽉 찬 Redo 로그가 덮어 쓰여지기 전에 Archive 로그 디렉토리로 백업
- Checkpint(CKPT): 마지막 체크포인트 시점 이후의 데이터베이스 변경 사항을 데이터 파일에 기록하도록 트리거링 및 헤더 저장
- Recoverer(RECO): 분산 트랜잭션 과정에 발생한 문제 해결

#### 데이터 저장 구조
- 블록(페이지): 데이터를 읽고 쓰는 단위
- 익스텐트: 공간을 확장하는 단위
- 세그먼트: 익스텐트 집합(익스텐트끼리 인접하지 않음)
- 테이블스페이스: 세그먼트를 담는 컨테이너로서, 여러 데이터파일로 구성

#### Undo 사용 목적
- Transaction Rollback
- Transaction Recovery
- Read Consistency
Snapshot Too Old

#### Redo 사용 목적
- Database Recovery
- Cache Recovery
- Fast commit
Log Force at commit, Fast Commit, Write Ahead Logging

#### 오라클 SGA 구성
- DB Buffer Cache, Redo Log Buffer, Library Cache, Dictionary Cache

#### 오라클 메모리 캐시
- DB 버퍼 캐시: 데이터블록, 인덱스블록, Undo 블록 캐싱
- 라이브러리 캐시: SQL, DB 저장형 함수/프로시저 트리거 캐싱
- 딕셔너리 캐시: 테이블, 인덱스, 데이터파일, 시퀀스 등 캐싱
- Result 캐시: SQL 결과집합을 캐싱

#### 버퍼 블록의 상태
- Free 버퍼: 비어있는 상태
- Dirty 버퍼: 아직 데이터파일에 기록되지 않아 동기화가 필요한 버퍼 블록
- Pinned 버퍼: 읽기 쓰기 작업을 위해 액세스
