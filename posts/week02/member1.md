# 2장

# 인덱스(Index)

## 1. 인덱스 개념

큰 테이블에서 소량의 데이터를 빠르게 검색할 때 사용하며, 특히 OLTP 환경에서 유용하다.

- 인덱스 스캔 과정에서 발생하는 비효율 최소화
- 테이블 액세스 횟수 감소 (= 랜덤 액세스 최소화)
- 인덱스가 정렬되어 있어 범위 스캔(Range Scan) 가능
- 일반적으로 B*Tree 인덱스*사용

## 2. 인덱스 탐색 과정

### 2-1. 인덱스 수직적 탐색

정렬된 인덱스 레코드 중 조건을 만족하는 첫 번째 레코드를 찾는 과정

- 인덱스 스캔 시작 지점을 찾는 과정
- 루트 블록 → 브랜치 블록 → 리프 블록 순서로 탐색

### 2-2. 인덱스 수평적 탐색

수직적 탐색 이후 조건에 맞는 인덱스 레코드를 찾는 과정

- 리프 블록은 앞뒤 블록의 주소를 가진 양방향 연결 리스트 구조
- 리프 블록 간 이동을 통해 범위 검색 가능

## 3. 결합 인덱스 (Composite Index)

여러 컬럼을 하나의 인덱스로 구성한 것

- 인덱스 컬럼의 순서가 중요할 수 있음
- 인덱스 선두 컬럼을 모두 `=` 조건으로 검색하는 경우 일반적으로 컬럼 순서와 관계없이 탐색 효율이 비슷함
- 단, 실제 블록 I/O는 데이터 분포 등에 따라 달라질 수 있음

## 4. 인덱스 사용 시 주의사항

### 4-1. Index Range Scan 조건

- 인덱스 선두 컬럼을 가공하지 않은 상태로 조건절에 사용해야 일반적인 Range Scan 가능
- 인덱스 컬럼 가공 시 정상적인 인덱스 탐색이 어려워질 수 있음

**Range Scan이 제한될 수 있는 경우**

- 인덱스 컬럼 가공
- `LIKE '%ABC%'` 형태의 중간값 검색
- `OR` 조건
- `IN` 조건
- `UNION ALL` 각 분기의 조건

※ `OR`, `IN`, `UNION ALL`이 있다고 해서 반드시 Range Scan이 불가능한 것은 아님

### 4-2. 형변환 주의

- 자동 형변환으로 인덱스 컬럼이 가공되면 인덱스 사용에 불리할 수 있음
- 가능하면 인덱스 컬럼의 자료형에 맞춰 비교값을 변환

## 5. 인덱스 스캔 방식

### 5-1. Index Range Scan

B*Tree 인덱스의 가장 일반적인 액세스 방식

- 루트에서 리프 블록까지 수직적 탐색
- 이후 필요한 범위만 수평적 탐색
- 인덱스 선두 컬럼을 가공하지 않은 상태로 조건절에 사용해야 일반적인 Range Scan 가능

### 5-2. Index Full Scan

인덱스 리프 블록 전체를 순서대로 스캔하는 방식

- 일반적으로 리프 블록의 시작점으로 이동한 후 전체를 수평적으로 탐색
- 인덱스 선두 컬럼이 조건절에 없는 경우에도 사용 가능
- 테이블 전체보다 인덱스 크기가 작으면 유리할 수 있음
- 인덱스 키 순서대로 읽으므로 Sort 연산 생략 가능
- 단, `ORDER BY`의 정렬 순서와 인덱스 순서가 일치해야 함

### 5-3. Index Unique Scan

Unique 인덱스를 이용해 단일 인덱스 레코드를 탐색하는 방식

- 수직적 탐색만으로 인덱스 레코드를 찾음
- Unique 인덱스의 전체 키 컬럼을 `=` 조건으로 검색할 때 사용
- 범위 검색 조건이면 Index Range Scan 사용

### 5-4. Index Skip Scan

인덱스 선두 컬럼이 조건절에 없어도 인덱스를 활용하는 방식

- 선두 컬럼의 값들을 구분하여 인덱스를 탐색
- 조건에 부합할 가능성이 있는 리프 블록을 선택적으로 접근
- 선두 컬럼의 Distinct Value가 적고, 후행 컬럼의 Distinct Value가 많을 때 유용
- 선두 컬럼이 범위 검색 조건인 경우에도 사용 가능

### 5-5. Index Fast Full Scan

인덱스 트리의 논리적인 순서를 무시하고 인덱스 세그먼트 전체를 읽는 방식

- Multiblock I/O 방식 사용
- 대량의 인덱스 블록을 읽을 때 유리
- 일반적으로 Index Full Scan보다 빠를 수 있음
- 인덱스 키 순서가 보장되지 않아 Sort 연산 생략 불가
- 쿼리에 필요한 컬럼을 모두 인덱스에서 처리할 수 있을 때 사용 가능
- 인덱스가 파티션되지 않아도 병렬 쿼리 가능

### 5-6. Index Range Scan Descending

Index Range Scan과 기본적으로 동일하지만 역방향으로 탐색하는 방식

- 리프 블록을 내림차순으로 스캔
- 인덱스 정렬 순서와 맞는 `ORDER BY DESC` 처리에 유리
- 별도 Sort 연산 생략 가능

## 핵심 정리

**인덱스 탐색 과정 2가지는?**
- 수직적 탐색: 인덱스 스캔 시작 지점을 찾는 과정 (루트 → 브랜치 → 리프)
- 수평적 탐색: 데이터를 찾는 과정

**인덱스 튜닝의 핵심 요소 2가지는?**
- 인덱스 스캔 효율화: 인덱스 스캔 과정에서 읽는 불필요한 블록 최소화
- 랜덤 액세스 최소화: 인덱스에서 ROWID를 이용한 테이블 액세스 횟수 감소

**ROWID 구성 요소는 ?**
- ROWID = 데이터 블록 주소(DBA) + 로우 번호
  - 데이터 블록 주소 = 데이터 파일 번호(데이터 파일 식별) + 블록 번호(데이터가 저장된 블록 위치)
  - 로우 번호 : 블록 내 순번
 
**인덱스 range scan 불가 이유 2가지는 ?**
- 인덱스 컬럼 가공한 경
- 인덱스 선두 컬럼이 조건절에 없는 경우

**인덱스 형변환**
- **숫자형 vs 문자형**
  - 숫자형의 우선순위가 높아 문자형을 숫자형으로 변환
  - 단, LIKE 연산자는 숫자형이 문자형으로 변환
  
- **날짜형 vs 문자형**
  - 일반적으로 문자형을 날짜형으로 변환

=> 인덱스 컬럼 기준으로 반대편 컬럼 또는 값을 정확히 형변환 해주길

**Index Full Scan을 사용하면 유리한 경우는 ?**
- 테이블 전체보다 인덱스 크기가 작은 경우
- Sort 연산 생략 가능한 경우

**Index Skip Scan이 불리한 경우는 ? (본인의 생각기술)**
- 인덱스 선두 컬럼의 Distinct Value가 많을 때
- 인덱스 후행 컬럼의 Distinct Value가 적을 때

**Index Fast Full Scan의 특징 2가지는 ?**
- Multiblock I/O 방식 사용
- 정렬되지 않
