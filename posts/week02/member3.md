## 2.1 인덱스 구조 및 탐색

### 인덱스 튜닝의 두 가지 핵심 요소

- **인덱스 스캔 효율화 튜닝**: 인덱스 스캔 과정에서 발생하는 비효율을 줄이는 것
- **랜덤 액세스 최소화 튜닝**: 테이블 액세스 횟수를 줄이는 것

인덱스를 많이 사용하는 OLTP 시스템에서는 디스크 I/O 중에서도 랜덤 I/O가 중요하다.

조인 메소드 중 가장 일반적인 NL 조인이 대량 데이터를 조인할 때 느린 이유도 랜덤 I/O 때문이다. 이를 보완하기 위해 소트 머지 조인이나 해시 조인 같은 방식이 사용된다.

### 인덱스 구조

DBMS는 일반적으로 B-Tree 인덱스를 사용한다.

**LMC (Leftmost Child)**

자식 노드 중 가장 왼쪽에 위치한 블.

LMC가 가리키는 주소로 찾아가면 키값을 가진 첫 번째 레코드보다 작거나 같은 레코드가 저장되어 있다.

리프 블록에 저장된 레코드는 키값 순으로 정렬되어 있으며, 테이블 레코드를 가리키는 주소값인 ROWID를 갖는다.

키값이 같으면 ROWID 순으로 정렬한다. ROWID는 DBA와 로우 번호로 구성되어 있기 때문에 테이블 레코드를 찾아갈 수 있다.

**ROWID 구성**

- ROWID = DBA + 로우 번호
- 데이터 블록 주소(DBA) = 데이터파일 번호 + 블록 번호
- 블록 번호: 데이터 파일 내에서 부여한 상대적 순번
- 로우 번호: 블록 내 순번

### 인덱스 탐색 과정

- **수직적 탐색**: 인덱스 스캔 시작 지점을 찾는 과정
- **수평적 탐색**: 실제 데이터를 찾는 과정

**수직적 탐색**

루트 블록에서부터 시작해서 찾고자 하는 레코드보다 크거나 같은 값을 만나면 직전 값의 레코드가 가리키는 하위 블록으로 내려간다.

이 과정을 반복하여 리프 블록에 도달한 후, 조건을 만족하는 첫 번째 레코드를 찾는다.

**수평적 탐색**

리프 블록에서 첫 번째 레코드를 찾으면, 찾고자 하는 데이터가 더 이상 나타나지 않을 때까지 리프 블록을 수평적으로 스캔한다.

인덱스 리프 블록끼리는 앞뒤 블록에 대한 주소값을 가지고 있으며, 양방향 연결 리스트로 구성되어 있다.

수평적으로 탐색하는 이유

1. 조건절을 만족하는 데이터를 모두 찾기 위해서
2. ROWID를 얻기 위해서 -> 인덱스를 스캔한 후 테이블에도 액세스하는데, 이때 ROWID가 필요함

### B-Tree 인덱스의 의미

B-Tree의 B는 Balanced를 의미한다.

어떤 값으로 탐색하더라도 인덱스 루트에서 리프까지 읽는 블록 수가 같다. 즉, 인덱스의 높이가 동일하다.

## 2.2 인덱스 기본 사용법

인덱스 기본 사용법은 INDEX RANGE SCAN을 이용하는 것이다.

확장 기능은 그 외의 인덱스 스캔 방식을 의미한다.

### 인덱스 컬럼 가공

인덱스 컬럼을 가공한다는 것은 조건절에 사용하는 컬럼을 가공하는 것을 의미한다.

예를 들어 `SUBSTR`, `NVL` 등의 함수를 사용하여 컬럼값을 변형하는 경우가 있다.

일반적으로 다음과 같은 조건은 INDEX RANGE SCAN을 수행하기 어렵고, 테이블 풀 스캔이 발생할 수 있다.

- OR 조건
- LIKE 조건

단, OR 조건은 UNION ALL을 이용하여 INDEX RANGE SCAN이 가능하도록 변경할 수 있다.

**예시**
``` sql
SELECT *
FROM USR
WHERE USR_ID = 'USER001'
   OR USR_NM = '홍길동';
```
``` sql
SELECT *
FROM USR
WHERE USR_ID = 'USER001'

UNION ALL

SELECT *
FROM USR
WHERE USR_NM = '홍길동'
  AND USR_ID <> 'USER001';
```

IN 조건도 OR 조건을 다르게 표현한 것이므로 UNION ALL을 사용하여 처리할 수 있다.

다만 IN 조건절에 대해서는 옵티마이저가 IN-List Iterator 방식을 사용한다.

IN-List Iterator는 IN 목록의 값만큼 INDEX RANGE SCAN을 반복하는 방식이다.

### 자동 형변환

인덱스에 등록된 컬럼이 문자형인데 숫자형으로 변환하여 비교하는 경우, 인덱스를 사용하지 못할 수 있다.

오라클에서는 숫자형과 문자형이 만나면 숫자형이 우선하며, 날짜형과 문자형이 만나면 날짜형이 우선한다.

따라서 날짜를 비교할 때는 날짜 포맷을 정확히 지정해 주는 코딩 습관이 필요하다.

**LIKE 연산자의 경우**

LIKE는 문자열 비교 연산자이므로 일반적인 자동 형변환과 다르게 동작한다.

이때는 숫자형 컬럼이 문자형으로 변환된다.

이러한 형변환 이슈로 애플리케이션 품질에 문제가 발생할 수 있다.

문자형 컬럼에 숫자로 변환할 수 없는 데이터가 존재하는 경우 오류가 발생하기도 한다.

### DECODE 함수의 자동 형변환

오라클에서 DECODE 함수를 처리할 때도 자동 형변환이 발생한다.

`DECODE(a, b, c, d)`는 a와 b가 같으면 c를 반환하고, 다르면 d를 반환한다.

이때 반환값의 데이터 타입은 세 번째 인자인 c를 기준으로 결정된다.

따라서 c가 문자형이고 d가 숫자형인 경우 d가 문자형으로 변환된다.

또한 c가 NULL인 경우 VARCHAR2로 취급한다.

따라서 데이터 타입을 명시적으로 지정해 주는 것이 좋다.

세 번째 인자에 NULL을 넣어야 하는 경우에도 `0`이나 `TO_NUMBER` 등을 활용하여 데이터 타입을 명확하게 지정할 수 있다. (급여 예시)

### 형변환과 성능

형변환 함수를 생략하면 연산 횟수가 줄어 효율적이라고 생각할 수 있다.

하지만 성능은 연산 횟수만으로 판단하는 것이 아니라 블록 I/O를 줄일 수 있는지 여부가 중요하다.

## 2.3 인덱스 확장 기능 사용법

### INDEX RANGE SCAN

가장 기본적인 인덱스 액세스 방식이다.

수직적으로 탐색하여 스캔 시작 지점을 찾은 후, 필요한 범위만 수평적으로 스캔한다.

인덱스 선두 컬럼을 가공하지 않은 상태로 조건절에 사용하면 INDEX RANGE SCAN이 가능한 형태가 된다.

단, 인덱스를 사용한다고 무조건 성능이 좋은 것은 아니다.

성능은 **인덱스 스캔 범위와 테이블 액세스 횟수를 얼마나 줄일 수 있는지**에 따라 결정된다.

### INDEX FULL SCAN

수직적 탐색 없이 리프 블록을 처음부터 끝까지 수평적으로 스캔하는 방식이다.

데이터 검색을 위한 최적의 인덱스가 없을 때 차선책으로 선택될 수 있다.

인덱스 선두 컬럼이 조건절에 없다면 일반적으로 TABLE FULL SCAN을 고려하지만, 테이블이 대용량인 경우 옵티마이저가 INDEX FULL SCAN을 선택할 수도 있다.

- 조건에 해당하는 데이터가 극히 일부라면 TABLE FULL SCAN보다 INDEX FULL SCAN이 유리할 수 있다.
- 수행 빈도가 높다면 해당 컬럼으로 인덱스를 생성하는 것이 더 나은 방법일 수 있다.
- 인덱스 컬럼 순서대로 결과가 정렬되므로 SORT ORDER BY 연산을 생략할 목적으로 사용할 수도 있다.

**FIRST_ROWS 힌트**

예시 쿼리에서 `/*+ FIRST_ROWS */` 힌트를 사용했기 때문에 대량의 데이터임에도 INDEX FULL SCAN이 선택된 경우가 있다.

FIRST_ROWS는 전체 결과를 모두 처리하는 시간보다 처음 몇 건의 결과를 빠르게 반환하는 데 중점을 두는 힌트다.

다만 INDEX FULL SCAN이 TABLE FULL SCAN보다 항상 빠른 것은 아니며, 오히려 전체 수행 시간은 더 느려질 수도 있다.

### INDEX UNIQUE SCAN

수직적 탐색만으로 데이터를 찾는 방식이다.

일반적으로 유니크 인덱스 컬럼을 `=` 조건으로 검색할 때 사용한다.

유니크 인덱스는 중복값이 입력되지 않도록 DBMS가 데이터 정합성을 관리한다.

따라서 조건에 해당하는 레코드를 한 건 찾으면 더 이상 탐색할 필요가 없다.

다음과 같은 경우에는 INDEX RANGE SCAN으로 처리된다.

- 유니크 인덱스를 사용하더라도 범위 검색 조건을 사용하는 경우
- 결합 유니크 인덱스에서 일부 컬럼만 조건으로 사용하는 경우

### INDEX SKIP SCAN

Oracle 9i부터 지원하는 방식으로, 인덱스 선두 컬럼이 조건절에 없어도 인덱스를 활용할 수 있는 스캔 방식이다.

**사용하기 유리한 조건**

- 선두 컬럼의 Distinct Value 개수가 적을 때
- 후행 컬럼의 Distinct Value 개수가 많을 때

예를 들어 성별과 사원번호로 결합 인덱스를 생성했다고 가정한다.

- 선두 컬럼: 성별 (남성, 여성 등 값의 종류가 적음)
- 후행 컬럼: 사원번호 (값의 종류가 많음)

이때 성별 조건 없이 사원번호만으로 조회하더라도 INDEX SKIP SCAN을 활용할 수 있다.

**동작 방식**

루트 또는 브랜치 블록에서 읽은 컬럼 값 정보를 이용하여 조건절에 부합하는 레코드가 존재할 "가능성이 있는" 리프 블록을 찾아 접근한다.

선두 컬럼의 값별로 탐색 범위를 나누어 필요한 부분을 스캔하는 방식이다.

예를 들어 성별이 남/여 지만 옵티마이저는 실제 데이터의 모든 값이 두 종류라는 것을 단정할 수 없으므로, 조건에 부합할 가능성이 있는 범위까지 탐색함..

**힌트**

```sql
/*+ INDEX_SS(테이블 별칭 인덱스명) */
/*+ NO_INDEX_SS(테이블 별칭 인덱스명) */
```

다음과 같은 경우에도 INDEX SKIP SCAN을 고려할 수 있다.

- 선두 컬럼에는 조건이 있지만 중간 컬럼에 조건이 없는 경우
- Distinct Value 개수가 적은 선두 컬럼들이 모두 조건절에 없는 경우
- 선두 컬럼에 부등호, BETWEEN, LIKE 등의 범위 검색 조건이 있는 경우

단, INDEX SKIP SCAN이 항상 유리한 것은 아니며 기본적으로는 INDEX RANGE SCAN을 목표로 인덱스를 설계하는 것이 좋다.

### INDEX FAST FULL SCAN

논리적인 인덱스 구조를 무시하고 인덱스 세그먼트 전체를 멀티블록 I/O 방식으로 스캔하는 방식이다.

**힌트**

```sql
/*+ INDEX_FFS(테이블 별칭 인덱스명) */
/*+ NO_INDEX_FFS(테이블 별칭 인덱스명) */
```

INDEX FULL SCAN은 인덱스 리프 블록의 논리적인 순서에 따라 스캔하지만, INDEX FAST FULL SCAN은 익스텐트에 저장된 순서 등을 기준으로 블록을 읽는다.

예를 들어 리프 블록이 1번부터 10번까지 있더라도 실제로는 서로 다른 익스텐트에 분산되어 있을 수 있다.

- INDEX FULL SCAN: 1 → 2 → 3 → 4 → ...
- INDEX FAST FULL SCAN: 1 → 4 → 2 → 5 → 10 → ...

실제 스캔 순서는 물리적인 저장 구조에 따라 달라질 수 있다.

**특징**

- 멀티블록 I/O를 사용하므로 대량의 인덱스 블록을 읽을 때 효과적이다.
- 인덱스 키 순서대로 정렬되지 않는다.
- 쿼리에 필요한 컬럼이 모두 인덱스에 포함되어 있어야 사용할 수 있다.

### INDEX FULL SCAN과 INDEX FAST FULL SCAN 비교

| 구분 | INDEX FULL SCAN | INDEX FAST FULL SCAN |
|---|---|---|
| 스캔 방식 | 인덱스 구조에 따라 스캔 | 세그먼트 전체 스캔 |
| 결과 순서 | 인덱스 키 순서 보장 | 결과 순서 보장 안 됨 |
| I/O 방식 | 싱글블록 I/O | 멀티블록 I/O |
| 병렬 스캔 | 일반적으로 제한적 (파티션 구성 등에 따라 다름) | 병렬 스캔 가능 |
| 조회 컬럼 | 인덱스에 포함되지 않은 컬럼도 테이블 액세스를 통해 조회 가능 | 인덱스에 포함된 컬럼만 조회 가능 |

### INDEX RANGE SCAN DESCENDING

인덱스를 뒤에서 앞으로 스캔하는 방식이다.

내림차순으로 정렬된 결과를 얻고 싶을 때 사용할 수 있다.

옵티마이저가 인덱스를 역방향으로 읽지 않는 경우 힌트를 사용하여 실행 경로를 변경할 수 있다.

**힌트**

```sql
/*+ INDEX_DESC(테이블 별칭 인덱스명) */
```
