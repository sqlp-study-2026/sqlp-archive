# 1장

1. SQL
   구조적, 집합적, 선언적인 질의 언어
   - SQL 옵티마이저: 프로시저를 만드는 DBMS 내부 엔진
   - SQL 최적화: DBMS 내부에서 프로시저를 작성하고 컴파일해서 실행 가능한 상태로 만드는 전 과정

2. SQL 실행
   1) SQL 파싱
   SQL Parser가 파싱을 진행
   - 파싱 트리 생성
   - Syntax 체크: 문법 오류 체크 
   - Semantic 체크: 의미상 오류 확인
   2) SQL 최적화
   SQL 옵티마이저는 통계정보를 바탕으로 다양한 실행 경로를 생성하여 비교한 후 가장 효율적인 하나를 선택
   3) 로우 소스 생성
      로우 소스 생성기가 실행가능한 코드/프로시저 형태로 포맷팅
   4) SQL 실행
   5) 결과 반환(Fetch)

3. SQL 옵티마이저
   최적의 데이터 액세스 경로 선택
   1) 목표를 위한 실행계획 정리
   2) 데이터 딕셔너리에 수집한 통계정보를 이용해 각 실행계획의 예상비용 산정
   3) 최저 비용의 실행계획 선택
   - 실행계획: SQL 옵티마이저가 생성한 처리절차를 확인할 수 있도록 트리구조로 표현한 것
   - 비용: 쿼리를 수행하는 동안 발생할 것으로 예상하는 I/O 횟수 또는 예상 소요시간
   - 옵티마이저 힌트: 액세스 경로를 바꿀 수 있음
   (ex. /*+ INDEX(A 고객_PK) */)
  
4. 소프트 파싱 vs 하드 파싱
   - 라이브러리 캐시: 내부 프로시저를 반복 재사용할 수 있도록 캐싱해두는 메모리 공간
   - 소프트 파싱: SQL을 캐시에서 찾아 바로 실행단계로 넘어가는 것
   - 하드 파싱: 캐시에 없어서 최적화 및 로우 소스 생성 단계까지 모두 거치는 것

5. 바인드 변수
   SQL은 전체 텍스트가 이름 역할을 하며, 처음 실행할 때 생성한 내부 프로시저를 라이브러리 캐시에 적재하여 공유/재사용.
   -바인드 변수: 파라미터를 Driven 방식으로 SQL 작성

7. I/O와 SQL 속도의 상관관계
   디스크에서 데이터를 읽어야 할 때 프로세스가 CPU를 반환하고 I/O Call이 종료될 때까지 대기 큐에 있는다.
   I/O Call 때문에 디스크 경합이 심해지고 대기 시간이 늘어니서 SQL이 느려지는 것이다.

8. 데이터베이스 저장 구조
   - 테이블스페이스: 세그먼트를 담는 공간
   - 세그먼트: 테이블, 인덱스, 파티션, LOB 저장 공간
   - 익스텐스: 연속된 데이터 블록의 집합; 공간 확장 단위
     =>테이블 입력하다가(세그먼트) 공간 부족해지면 테이블스페이스로부터 익스텐트(데이터 블록 집합)를 추가로 할당
   - 데이터 블록: 데이터 I/O 단위
   
9. Sequential Access vs Random Access
    - 시퀀셜 액세스
      논리적 또는 물리적으로 연결된 순서에 따라 차례대로 블록을 읽는 방식
      리프 블록이 가지는 앞뒤를 가리키는 주소값에 따라 순차적으로 스캔
      [참고]익스텐트 맵에서 각 익스텐트의 첫번째 블록 주소값을 얻어 해당 블록 뒤를 연속해서 순서대로 읽는 것이 Full Table Scan
    - 랜덤 액세스
      순서 없이 한 블록씩 접근하는 방식

10. 논리적 I/O vs 물리적 I/O
    SQL 성능 향상을 위해 디스크 I/O를 줄이기 위해 DB 버퍼캐시를 사용
    - 논리적 블록 I/O
      SQL을 처리하는 과정에서 발생한 총 블록 I/O
      논리적 I/O 횟수 = 메모리 I/O 횟수(DB 버퍼캐시에서 읽은 횟수)

    - 물리적 블록 I/O
      디스크에서 발생한 총 블록 I/O
      버퍼캐시 히트율(BCHR)
      읽은 전체 블록 중 물리적 디스크 I/O 없이 바로 메모리에서 찾은 비율
  => 논리적 I/O를 줄여 물리적 I/O을 줄이는 것이 곧 SQL 튜닝

11. Single Block I/O vs Multiblock I/O
    디스크 I/O
    - Single Block I/O
      한 번에 한 블록씩 요청해서 메모리에 적재하는 방식
      인덱스 이용 시 사용; 인덱스는 소량 데이터 읽을 때 효율적.
    - Multiblock I/O
      한 번에 여러 블록씩 요청해서 메모리에 적재
      디스크 상에 블록과 동일 익스텐트에 속한 블록들을 한번에 읽어 캐시에 미리 적재
      인덱스 없이 테이블 전체 스캔 시 사용; 많은 데이터를 읽을 때 효율적.

12. Table Full Scan vs Index Range Scan
    - Table Full Scan
      테이블 전체를 읽어서 원하는 데이터를 찾는 방식
      시퀀셜 엑세스와 Multiblock I/O 방식으로 디스크 블록을 읽음
      즉, 한 블록에 속한 모든 레코드를 한번에 읽어서 캐시에 없으면 인접한 여러 블록을 한번에 I/O하는 메커니즘
      => 큰 테이블에서 소량 데이터 찾을 때 비효율적
    - Index Range Scan
      인덱스에서 '일정량'을 스캔하여 ROWID로 테이블 레코드를 찾는 방식
      랜덤 액세스와 Single Block I/O 방식으로 디스크 블록 읽음
      즉, 캐시에서 못찾으면 레코드 하나를 찾기 위해 매번 디스크 I/O Call 발생하는 매커니즘
      => 많은 데이터를 읽을 때 비효율적
      => 읽을 데이터가 일정량 넘어가면 인덱스보다 full scan이 더 유리

13. 캐시 탐색 메커니즘
    버퍼 캐시에서 블록을 찾을 때, 해시 알고리즘으로 버퍼 헤더를 찾고, 거기서 얻은 포인터로 버퍼 블록을 액세스하는 방식
