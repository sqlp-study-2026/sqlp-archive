## 1.1 SQL 파싱과 최적화

### SQL 최적화

DBMS 내부에서 SQL을 실행하기 위한 프로시저를 생성하고 컴파일하여 실행 가능한 상태로 만드는 전 과정.

**1) SQL 파싱 (Parsing)**

파서가 SQL 문장을 분석하여 파싱 트리를 생성 -> Syntax Check -> Semantic Check 함

- Syntax Check (문법 검사): 사용할 수 없는 키워드, 잘못된 문법이나 순서 등 문법적 오류 확인
- Semantic Check (의미 검사): 존재하지 않는 테이블이나 컬럼 참조 여부, 객체 접근 권한 등 의미적 오류 확인

**2) SQL 최적화 (Optimization)**

옵티마이저가 하는 일.. 다양한 실행 경로를 생성해서 가장 효율적이라고 판단되는 실행 경로를 선택.

**3) 로우 소스 생성 (Row Source Generation)**

옵티마이저가 선택한 실행 경로를 실제 실행 가능한 형태의 코드 또는 프로시저로 생성하는 단계.

### 실행계획 (Execution Plan)

옵티마이저가 생성한 SQL 처리 절차를 사용자가 확인할 수 있도록 트리 구조로 표현한 것이다.

필요한 경우 SQL이나 힌트를 이용해 실행 경로를 조정할 수 있음.

실행계획에 표시되는 비용은 SQL 수행 시 예상되는 자원 사용량을 수치화한 거고 실제랑 다를 수 있음.

### 옵티마이저 힌트 (Optimizer Hint)

통계정보만으로 파악하기 어려운 데이터 특성이나 업무 특성을 개발자가 알고 있는 경우, 힌트를 사용하여 옵티마이저의 실행 경로 선택에 영향을 줄 수 있다.

**작성 방법**

SQL 주석 기호(웬만하면 /**/ 로..)에 `+`를 추가하여 작성한다.

```sql
/*+ INDEX(인덱스명1, 인덱스명2 ) */ <- 가능
/*+ INDEX(인덱스명1)  INDEX( 인덱스명2 ) */ <- 가능
/*+ INDEX(인덱스명1) , INDEX( 인덱스명2 ) */ <- 첫번째만 유효
```

**테이블 힌트 작성**

```sql
/*+ FULL(테이블명) */ <- 가능
/*+ FULL(스키마.테이블명) */ <- 스키마 사용 x
SELECT /*+ FULL(테이블명) */ <- 불가.. alias했으면 그걸로 명시해야됨
FROM 테이블명 A
```

## 1.2 SQL 공유 및 재사용

### 라이브러리 캐시 (Library Cache)

SQL 파싱, 최적화 및 로우 소스 생성 과정을 거쳐 만들어진 실행 관련 정보를 반복 재사용할 수 있도록 캐싱하는 메모리 공간이다.

SGA(System Global Area)의 구성 요소인 Shared Pool에 포함된다.

SQL 실행 시 라이브러리 캐시에 재사용 가능한 실행 정보가 있는지 확인한다.

- **소프트 파싱 (Soft Parsing)**: 라이브러리 캐시에 있으면 가져와서 실행
- **하드 파싱 (Hard Parsing)**: 라이브러리 캐시에 없어서 파싱 및 최적화 과정부터 다시 수행.

하드 파싱은 CPU 자원을 많이 소비하는 작업 중 하나

### 옵티마이저가 사용하는 정보

- 테이블, 컬럼, 인덱스 구조에 대한 기본 정보
- 오브젝트 통계: 테이블 통계, 인덱스 통계, 컬럼 통계
- 시스템 통계: CPU 속도, Single Block I/O 속도, Multiblock I/O 속도 등
- 옵티마이저 관련 파라미터

데이터베이스의 처리 과정은 I/O 작업에 많은 영향을 받으며, SQL을 실행할 때마다 파싱과 최적화를 반복하는 것은 비효율적이다.

꾸역꾸역 가져와서 생성한 내부적인 프로시저를 한번만 사용하면.. 넘 아깝.. -> 라이브러리캐시 잘 사용하자

### 바인드 변수 (Bind Variable)의 중요성

사용자 정의 함수, 프로시저, 트리거 등은 생성 시 이름이 부여되고 데이터베이스 객체로 관리된다. 실행 시 라이브러리 캐시에 관련 정보가 적재되어 여러 사용자가 공유할 수 있다.

반면 일반 SQL은 SQL 문장 자체를 기준으로 실행 정보를 관리하기 때문에 값이 달라지면 매번 생성하고 그마저도 캐시 공간 부족하면 비워냄...

**책 예시**

사용자 아이디로 정보 조회할 때 자바단에서 db 쿼리 실행할 때 그냥 파라미터로 처리하면 아이디 달라져서 다른 sql로 인식하는데 바인드 함수 사용하면 라이브러리 캐시 쌓이고 그 이후로는 캐싱 공유함

```sql
SELECT *
FROM USR
WHERE USR_ID = ?;
```

SQL 문장은 동일하게 유지하고 실행 시점에 값만 전달한다.

따라서 동일한 실행 정보를 여러 사용자가 재사용할 수 있어 하드 파싱을 줄이는 데 도움이 된다.

## 1.3 데이터 저장구조 및 I/O 메커니즘

I/O 튜닝은 SQL 튜닝에서 매우 중요한 부분이다.

### 프로세스 생명주기와 I/O

디스크 I/O가 발생하면 OS가 I/O 작업을 처리하는 동안 서버 프로세스는 피피쿨(대기) 상태에 들어간다.

I/O 작업이 완료되면 다시 작업을 수행한다.

따라서 I/O 작업이 많아지면 프로세스가 대기하는 시간도 증가하여 SQL 수행 시간이 길어질 수 있다.

### 데이터 저장 구조

데이터를 저장하기 위해 테이블스페이스를 생성하고 그 안에 세그먼트를 저장한다.

**테이블스페이스 → 세그먼트 → 익스텐트 → 블록**

- **테이블스페이스 (Tablespace)**: 세그먼트를 담는 논리적인 저장 공간
- **세그먼트 (Segment)**: 테이블, 인덱스 등 저장 공간이 필요한 데이터베이스 객체
- **익스텐트 (Extent)**: 공간을 확장하는 단위이며, 연속된 데이터 블록의 집합
- **블록 (Block)**: 데이터를 읽고 쓰는 기본 단위
- **데이터파일 (Datafile)**: 테이블스페이스의 데이터를 저장하는 물리적인 OS 파일

하나의 세그먼트는 여러 익스텐트로 구성된다.

테이블이나 인덱스에 데이터를 저장하다가 공간이 부족해지면 해당 테이블스페이스에서 익스텐트를 추가 할당받는다.

보통 하나의 익스텐트에 하나의 테이블이 독점.. 익스텐트 자체는 같이 있지만 익스텐트끼리는 서로 연속된 위치에 존재하지 않을 수 있다.

파티션 테이블은 일반적으로 각 파티션이 별도의 세그먼트를 구성한다.

### 블록 단위 I/O

데이터베이스는 블록 단위로 데이터를 읽고 쓴다.

특정 레코드의 1바이트만 필요하더라도 해당 데이터가 포함된 블록 전체를 읽어야 한다.

### 시퀀셜 액세스 (Sequential Access) vs 랜덤 액세스 (Random Access)

**시퀀셜 액세스**

논리적 또는 물리적으로 연결된 순서에 따라 블록을 순차적으로 읽는 방식이다.

- 인덱스 리프 블록은 앞뒤 블록의 주소 정보를 가지고 있어 이를 따라 순차적으로 스캔할 수 있다.
- 테이블은 인덱스와 달리 블록 간의 논리적인 연결 구조가 없음 -> 세그먼트에 할당된 익스텐트 목록을 헤더에 맵으로 관리함. 이를 통해 각 익스텐트의 시작 블록 주소를 확인하고 순차적으로 읽을 수 있다.
- ex) 테이블 풀 스캔

**랜덤 액세스**

논리적 또는 물리적인 순서를 따르지 않고 필요한 블록에 개별적으로 접근하는 방식이다.

인덱스에서 ROWID를 얻어 실제 테이블 블록을 찾아가는 방식이 대표적이다. 자세한 건 나중에

### DB 버퍼캐시 (Database Buffer Cache)

- 라이브러리 캐시: SQL, 실행계획, 저장형 함수 및 프로시저 등의 실행 관련 정보를 캐싱하는 "코드 캐시"
- 버퍼캐시: 데이터 블록을 캐싱하는 "데이터 캐시"

반복적인 디스크 I/O를 줄이는 것이 목적

버퍼캐시는 서버 프로세스와 데이터파일 사이에서 데이터 블록을 캐싱함

최초에는 디스크에서 데이터를 읽고, 이후 동일한 블록에 접근할 때는 버퍼캐시에서 재사용.

### 논리적 I/O와 물리적 I/O

**논리적 I/O (Logical I/O)**

SQL을 처리하면서 DB 버퍼캐시를 통해 읽은 전체 블록 수이다.

일반적으로 메모리 버퍼캐시를 경유하기 때문에 메모리 I/O라고도 부른다.

**물리적 I/O (Physical I/O)**

디스크에서 발생한 블록 I/O이다. 짱느림..

필요한 블록을 버퍼캐시에서 찾지 못하면 디스크에 접근하여 읽어온다.

- 논리적 I/O: SQL 수행 중 버퍼캐시를 통해 읽은 전체 블록 수 (예시: 거리에 대한 자전거바퀴 회전수)
- 물리적 I/O: 디스크에서 실제 읽어온 블록 수 (예시: 역풍 순풍... 어쩌구.. 등등)

물리적 I/O는 버퍼캐시의 상태에 따라 SQL을 실행할 때마다 달라질 수 있다.

### 버퍼캐시 히트율 (Buffer Cache Hit Ratio, BCHR)

디스크 I/O를 수반하지 않고 버퍼캐시에서 데이터를 찾은 비율이다.

물리적 I/O가 성능에 직접적인 영향을 주지만, 실질적인 SQL 튜닝에서는 논리적 I/O를 줄이는 것이 중요하다.

동일한 SQL이라도 불필요하게 많은 블록을 읽으면 물리적 I/O가 발생할 가능성도 높아지기 때문이다.

**핵심: SQL 튜닝은 접근하는 블록의 개수를 줄여 논리적 I/O를 감소시키는 것이 중요하다.**

단, BCHR이 높다고 무조건 SQL이 효율적인 것은 아니다. 인덱스 NL 조인처럼 동일한 블록을 반복해서 읽는 비효율이 발생할 수도 있다. (나중에 설명)

### SQL 트레이스의 I/O 항목

SQL 트레이스에서 확인하는 주요 항목은 다음과 같다.

- Query: Consistent 모드로 읽은 블록 수
- Current: Current 모드로 읽은 블록 수
- Disk: 디스크에서 읽은 블록 수

Query + Current 합산한 값 논리적 블록 수

### 싱글블록 I/O와 멀티블록 I/O

**싱글블록 I/O (Single Block I/O)**

한 번의 I/O 요청으로 하나의 블록을 읽는 방식이다.

- 소량의 데이터를 읽을 때 유용하다.
- 인덱스를 이용할 때 주로 사용한다.

인덱스 조회 과정은 다음과 같다.

1. 인덱스 루트 블록 읽기
2. 브랜치 블록 읽기
3. 리프 블록 읽기
4. 리프 블록에서 얻은 ROWID로 테이블 블록 읽기

**멀티블록 I/O (Multiblock I/O)**

한 번의 I/O 요청으로 여러 개의 인접한 블록을 읽는 방식이다.

테이블 풀 스캔처럼 많은 데이터 블록을 읽을 때 효율적이다.

버퍼캐시에서 특정 블록을 찾지 못해 디스크 I/O가 발생하면 해당 블록과 인접한 블록을 함께 읽어 메모리에 적재할 수 있다.

- 대량의 데이터를 읽을 때 효율적이다.
- 한 번에 여러 블록을 읽어 I/O 요청 횟수를 줄일 수 있다.
- 읽을 블록이 익스텐트 경계 등에 도달하면 연속된 범위의 읽기가 제한될 수 있다. (예시: 수레에 자리 남아도 벽돌가게에 벽돌 없으면 그냥 감)
- 이미 버퍼캐시에 존재하는 블록이 있으면 싱글블록 I/O와 멀티블록 I/O가 혼합되어 발생할 수도 있다.

### 테이블 풀 스캔과 인덱스 레인지 스캔

**테이블 풀 스캔 (Table Full Scan)**

테이블에 속한 전체 데이터 블록을 읽어 조건에 맞는 데이터를 찾는 방식이다.

**인덱스 레인지 스캔 (Index Range Scan)**

인덱스의 일정 범위를 스캔하고, 해당 과정에서 얻은 ROWID를 이용하여 실제 테이블 레코드를 찾아가는 방식이다.

| 구분 | 테이블 풀 스캔 | 인덱스 레인지 스캔 |
|---|---|---|
| 접근 방식 | 테이블 전체 블록 순차 접근 | 인덱스 범위 스캔 후 ROWID로 접근 |
| 주요 I/O | 멀티블록 I/O | 싱글블록 I/O |
| 유리한 경우 | 대량 데이터 조회 | 소량 데이터 조회 |

큰 테이블에서 소량의 데이터를 찾을 때는 인덱스가 유리할 수 있다.

반대로 많은 데이터를 읽어야 한다면 인덱스 레인지 스캔은 ROWID를 이용한 랜덤 액세스가 반복되므로 테이블 풀 스캔보다 비효율적일 수 있다.

스토리지 성능이 좋아지더라도 반복적인 랜덤 액세스에 따른 비효율이 완전히 해결되는 것은 아니다.

### 캐시 탐색 메커니즘

Direct Path I/O 등의 예외를 제외하면 데이터 블록 I/O는 일반적으로 메모리 버퍼캐시를 경유한다.

다음 작업에서 버퍼캐시 탐색이 발생한다.

1. 인덱스 루트 블록 읽기
2. 인덱스 브랜치 블록 읽기
3. 인덱스 리프 블록 읽기
4. ROWID를 이용한 테이블 블록 읽기
5. 테이블 풀 스캔

**해시 알고리즘을 이용한 탐색**

버퍼캐시에서 블록을 찾을 때 해시 알고리즘을 사용한다.

1. DBA(Data Block Address)를 해시 함수에 입력한다.
2. 반환된 해시 값으로 해시 체인을 찾는다.
3. 해당 체인에서 블록 정보를 탐색한다.
4. 블록이 캐시에 존재하면 버퍼 블록에 접근한다.
5. 존재하지 않으면 디스크에서 블록을 읽어온다.

해시 체인의 특징은 다음과 같다.

- 같은 입력값은 항상 동일한 해시 체인으로 연결된다.
- 다른 입력값이 동일한 해시 체인으로 연결될 수 있다.
- 체인 내부의 정렬은 보장되지 않는다.

**래치 (Latch)**

버퍼캐시는 여러 프로세스가 공유하는 자원이지만, 공유 메모리 구조를 여러 프로세스가 동시에 변경하면 문제가 발생할 수 있다.

이를 방지하기 위해 래치라는 동기화 메커니즘을 사용한다.

**캐시 버퍼 체인 래치 (Cache Buffers Chains Latch)**

DBA를 해시 함수에 입력하여 해시 체인을 찾는 과정에서 해당 체인 구조를 보호하는 역할을 한다.

다른 프로세스가 체인 구조를 동시에 변경하지 못하도록 보호한다.

**버퍼 락 (Buffer Lock)**

해시 체인뿐 아니라 개별 버퍼 블록에도 동시 접근을 제어하는 메커니즘이 필요하다.

버퍼 락은 개별 버퍼 블록에 대한 접근과 변경을 보호한다.

**래치와 버퍼 락의 차이**

| 구분 | 보호 대상 | 역할 |
|---|---|---|
| 캐시 버퍼 체인 래치 | 해시 체인 구조 | 블록 탐색을 위한 체인 구조 보호 |
| 버퍼 락 | 개별 버퍼 블록 | 블록에 대한 동시 접근 및 변경 제어 |
| 로우 락 | 테이블의 개별 행 | 트랜잭션 간 동일 행의 동시 변경 제어 |

래치와 버퍼 락은 서로 다른 목적의 동기화 메커니즘이다.

버퍼캐시는 공유 자원이기 때문에 이러한 동기화 과정에서 경합이 발생할 수도 있다.

결국 불필요한 블록 접근 자체를 줄이는 것이 I/O와 동시성 측면에서 모두 중요하다.
